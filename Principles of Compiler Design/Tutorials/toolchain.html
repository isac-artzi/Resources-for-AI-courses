The Toolchain

make, Git and GitHub, flex, and bison — the four tools this course runs on, and the handful of things about each that actually cause trouble.

All topics  ›  The toolchain

Four tools, none of which is compiler theory, all of which will cost you time if you learn them by trial and error. Each tab below is self-contained; link straight to one with #make, #git, #flex or #bison on the end of this page's address.

Check your toolchain first
flex --version && bison --version && gcc --version && make --version && which spim

Project 1 asks for evidence that these are installed and working, so run this in week 1. Anything missing is far easier to fix now than the night before a deadline.

What make is for

Your compiler is nine source files that produce eight intermediate files and one executable. Rebuilding all of it after changing one line is slow and, worse, it is the kind of slow that makes you stop rebuilding. make reads a description of what depends on what, compares timestamps, and re-runs only the commands whose inputs have changed.

The anatomy of a rule

target : prerequisites
<TAB>recipe

Three parts. The target is a file to be produced. The prerequisites are the files it is made from. The recipe is the shell command that makes it. make runs the recipe when the target is missing, or when any prerequisite is newer than the target.

ast.o : ast.c ast.h
	gcc -g -Wall -c ast.c
The recipe line must begin with a TAB

Not spaces. This is the single most common Makefile error and the message is unhelpful:

Makefile:12: *** missing separator.  Stop.

If you see that, line 12 begins with spaces. Most editors can be told to keep real tabs in Makefiles; if yours converts silently, check with cat -A Makefile — a real tab shows as ^I.

Variables

CC     = gcc
CFLAGS = -g -Wall
OBJS   = lex.yy.o parser.tab.o main.o ast.o symtab.o semantic.o codegen.o tac.o

minicompiler : $(OBJS)
	$(CC) $(CFLAGS) -o minicompiler $(OBJS)

Defined with =, used with $(NAME). Worth doing for anything repeated: changing CFLAGS in one place then applies to every compile.

Automatic variables

Inside a recipe, make defines several variables for you. Three are worth knowing:

VariableMeansIn <code>ast.o : ast.c ast.h</code>
$@the targetast.o
$<the first prerequisiteast.c
$^all prerequisitesast.c ast.h
ast.o : ast.c ast.h
	$(CC) $(CFLAGS) -c $< -o $@

Pattern rules

One rule for a whole class of files. % matches any stem:

%.o : %.c
	$(CC) $(CFLAGS) -c $< -o $@

That single rule builds every .o from its .c. You still add specific rules to declare extra prerequisites — header files, mostly — and the two combine:

semantic.o : semantic.c semantic.h ast.h symtab.h trace.h

Note there is no recipe on that line: it adds prerequisites to the target, and the pattern rule supplies the command. Getting the header dependencies right is what makes make rebuild correctly after you edit an .h file — and getting them wrong produces the maddening bug where the build succeeds but the binary behaves as though your change never happened.

Phony targets

Some targets are not files. clean never produces a file called clean, so if a file by that name ever appeared, make clean would decide there was nothing to do. Declaring it phony prevents that:

clean :
	rm -f $(TARGET) $(OBJS) lex.yy.c parser.tab.c parser.tab.h

.PHONY : all clean test

The course Makefile, line by line

Here is what your compiler's Makefile is actually saying:

CC     = gcc                     # the compiler to use
LEX    = flex
YACC   = bison
CFLAGS = -g -Wall                # debug symbols, and all warnings

TARGET = minicompiler
OBJS   = lex.yy.o parser.tab.o main.o ast.o symtab.o semantic.o codegen.o tac.o

all : $(TARGET)                  # the DEFAULT target — first in the file

$(TARGET) : $(OBJS)              # link everything into the executable
	$(CC) $(CFLAGS) -o $(TARGET) $(OBJS)

lex.yy.c : scanner.l parser.tab.h   # NOTE the second prerequisite
	$(LEX) scanner.l

parser.tab.c parser.tab.h : parser.y
	$(YACC) -d parser.y
The one non-obvious dependency

lex.yy.c depends on parser.tab.h as well as on scanner.l. The scanner returns token numbers, and those numbers are assigned by bison and written into the header. Without that prerequisite, a clean build can run flex before bison, and you get a wall of errors about INT and PRINT being undeclared — in a file you did not write. Delete the prerequisite and run make clean && make -j4 to see it happen.

Flags worth knowing

make            # build the first target
make test       # build and run a named target
make clean      # delete what make produced
make -n         # DRY RUN: print the commands without running them
make -B         # rebuild everything, ignoring timestamps
make -j4        # run four recipes at once — exposes missing dependencies
make -d         # explain every decision (very verbose)

make -n is the one to reach for when a build does something you did not expect: it shows exactly which commands would run, in order, without running them.

A useful habit: always test with make -j

Parallel builds only work if your dependency graph is complete. If make -j4 fails intermittently but make always succeeds, you have a missing prerequisite that serial builds hide by luck of ordering. Finding it now is much easier than finding it the night before a deadline on a teammate's machine.

The mental model

Git confuses people because four different places hold your work, and most commands move things between two of them. Learn the four and most of the confusion goes away.

git status reports where everything currently sits. When something is confusing, run it first — it is the single most useful command in Git, and it usually suggests the command you want next.

First-time setup

git config --global user.name  "Your Name"
git config --global user.email "you@example.com"
git config --global init.defaultBranch main

The name and email are stamped into every commit you make, permanently. Set them before your first commit rather than after.

The daily loop

git status                    # what has changed?
git add ast.c ast.h           # stage specific files
git add -A                    # or stage everything, including deletions
git commit -m "add createBinOp and wire it into the grammar"
git push                      # send commits to GitHub

git pull                      # get teammates' commits before you start work
git log --oneline -10         # recent history
git diff                      # what have I changed but not staged?
git diff --cached             # what is staged and about to be committed?
Pull before you start, push when you finish

Most merge pain on a team project comes from working for three days on a stale copy. Pulling at the start of each session costs nothing and prevents nearly all of it.

What must never be committed

Build artifacts. They are large, they change on every build, and they conflict constantly because everyone's differ. In this course that means:

*.o                 # object files
minicompiler        # the executable
lexer
lex.yy.c            # generated by flex — regenerate, do not store
parser.tab.c        # generated by bison
parser.tab.h
parser.output
*.s                 # assembly your compiler emitted while testing
*.tac
.DS_Store

Put those in a file named .gitignore at the top of the repository and commit that. One is provided in your starter code.

Ignoring a file does not untrack it

.gitignore only affects files Git is not already tracking. If you committed minicompiler before adding the rule, it stays tracked. Remove it from the repository while keeping it on disk:

git rm --cached minicompiler
git rm -r --cached *.o
git commit -m "stop tracking build artifacts"

Check what you are about to publish before you push:

git ls-files | grep -E '\.o$|minicompiler|lex\.yy\.c|parser\.tab\.'

Anything that prints is tracked and should not be.

Dividing the work

Divide by phase, not by file. Each phase has a clean interface, so each person owns a boundary, can work without blocking the others, and has something coherent to explain in their video. Dividing by file gives everyone a piece of everything and nobody an account of anything.

Merge conflicts

Two people changed the same lines. Git stops and marks the file:

<<<<<<< HEAD
    $$ = createBinOp('+', $1, $3);
=======
    $$ = createBinOp('+', $1, $3); free($2);
>>>> origin/main

Everything between <<<< and ==== is yours; everything between ==== and >>>> is theirs. Edit the file so it contains what you actually want — often a combination — delete all three marker lines, then:

git add parser.y
git commit
Conflict markers left in a file are a compile error

If your build suddenly fails with a syntax error on a line reading <<<<<<< HEAD, you resolved a conflict and missed one. grep -rn '<<<<<<<' . finds them all.

reset --hard followed by a force-push discards commits other people may already have. On anything shared, use git revert, which undoes the change by adding a new commit and leaves history intact.

What flex does

You give it patterns and actions; it writes a C function called yylex() that reads characters and runs the action of whichever pattern matches. The theory — regular expressions, NFA, DFA, and the two rules that break ties — is in the Topic 1 lecture notes. This is the mechanics.

The three sections

%{
  /* C code copied verbatim near the top of lex.yy.c:
     includes, globals, helper functions the actions call */
#include "parser.tab.h"
%}

%option noyywrap
%option yylineno

digit   [0-9]
letter  [a-zA-Z_]
id      {letter}({letter}|{digit})*

%%
"int"        { return INT; }
{id}         { yylval.str = strdup(yytext); return ID; }
[ \t\n]+     { /* skip whitespace: no return, so scanning continues */ }
.            { fprintf(stderr, "bad character '%s'\n", yytext); }
%%

/* user code: copied verbatim to the bottom */

Writing rules

A rule is a pattern, whitespace, then an action in braces. Two hard formatting rules:

  • The pattern must start in column 1. An indented line in the rules section is treated as C code to be copied out, not as a rule.
  • The action must start on the same line as the pattern.
unrecognized rule

This message almost always means a line in the rules section starts at column 1 but is not a valid pattern — most often a stray comment. Comments in the rules section must be indented, or flex tries to parse them as a pattern.

Patterns

PatternMatches
"int"the literal characters — quoting turns off all special meaning
[0-9]+one or more digits
[a-zA-Z_][a-zA-Z0-9_]*an identifier
{id}whatever the named definition id was defined as
.any character except newline
"//".*a line comment
"/*"([^*]|\*+[^*/])*\*+"/"a block comment, possibly multi-line

Quote anything with punctuation in it. "+" matches a plus sign; a bare + is the one-or-more operator and will not do what you want.

What an action can use

NameIs
yytextthe characters that matched, as a C string
yylenghow many characters matched
yylinenothe current line number — with %option yylineno
yylvalwhere to put the token's value for bison
return X;hand token X to the parser and pause
no returncontinue scanning — this is how whitespace is skipped
yytext is reused

It points into flex's own buffer, which is overwritten by the next token. If the parser will need the text later — for identifiers and numbers — you must copy it: yylval.str = strdup(yytext);. Storing the pointer instead produces an AST full of identifiers that have all mysteriously become the same string, and it is one of the hardest bugs in this course to track down.

Options

Columns, which flex does not track

yylineno is maintained for you. Columns are not, and a line number alone is not an exact location on a line holding three statements. Keep a counter yourself, and advance it in every action — including the ones that produce no token:

static int col = 1;

static void advance(const char *s, int n) {
    for (int i = 0; i < n; i++) {
        if (s[i] == '\n')      { col = 1; }
        else if (s[i] == '\t') { col += 4; }
        else                    { col++; }
    }
}

Forget to call it from the block-comment rule and every line number after the first multi-line comment is wrong — with no error to tell you.

Talking to bison

The two tools meet in one file. Bison's -d flag writes parser.tab.h, which defines the token numbers and the yylval union. The scanner includes it:

%{
#include "parser.tab.h"
%}

This is why the Makefile makes lex.yy.c depend on parser.tab.h, and why running flex before bison on a clean tree fails with undeclared identifiers.

Debugging a scanner

flex scanner.l              # writes lex.yy.c
flex -d scanner.l           # trace: prints every rule that fires

Or simply put a printf in the actions temporarily. The instructor's Topic 1 lexer prints a token table, which is the same idea made permanent — and a token table is by far the fastest way to see what your scanner is actually doing.

What bison does

You give it a grammar with actions; it writes a C function called yyparse() that calls yylex() for tokens and runs your action each time it recognizes a rule. The theory — context-free grammars, shift-reduce parsing, LALR, and where conflicts come from — is in the Topic 2 lecture notes. This is the mechanics.

The four sections

%{
  /* C copied verbatim: includes, globals, forward declarations */
#include "ast.h"
extern int yylex(void);
void yyerror(const char *s);
ASTNode *root = NULL;
%}

%union {                       /* the possible types of a symbol's value */
    int num;
    char *str;
    struct ASTNode *node;
}

%token <num> NUM               /* NUM carries an int   */
%token <str> ID                /* ID carries a string  */
%token INT PRINT               /* these carry nothing  */
%type  <node> expr stmt        /* non-terminals carry AST nodes */

%left '+' '-'                  /* precedence, lowest first */
%left '*' '/'

%%
stmt : ID '=' expr ';'   { $$ = createAssign($1, $3); free($1); }
     ;
expr : expr '+' expr     { $$ = createBinOp('+', $1, $3); }
     | NUM               { $$ = createNum($1); }
     ;
%%

void yyerror(const char *s) { fprintf(stderr, "line %d: %s\n", yylineno, s); }

$$ and $1: where values come from

Inside an action, $n is the value of the nth symbol on the right of the rule, and $$ is the value this rule produces. Count the symbols including the punctuation:

stmt : ID   '='   expr   ';'
       $1    $2     $3     $4     ->  $$

The types come from the %union and the %token / %type declarations. If you forget to declare a non-terminal's type, you get:

$$ of 'expr' has no declared type

The fix is a %type <node> expr line. This is the second most common bison error after conflicts.

Children are already built when the parent's action runs

Bison reduces innermost-first, so by the time the action for expr '+' expr executes, $1 and $3 already point at complete subtrees. You never write tree-walking code to build the tree — you only ever assemble one node from pieces that exist. Topic 2 §6 explains why this works: it is a syntax-directed definition using only synthesized attributes.

Precedence and associativity

%left  '+' '-'      /* declared FIRST  = binds loosest */
%left  '*' '/'
%right UMINUS       /* declared LAST   = binds tightest */
  • Later declarations bind tighter. The order of these lines is the entire precedence specification.
  • %left makes a - b - c group as (a - b) - c; %right would give a - (b - c), which is a different number.
  • %nonassoc makes a < b < c a syntax error rather than something surprising.

%prec

A rule takes the precedence of its last terminal, which is wrong for unary minus — the rule '-' expr would inherit binary minus. %prec overrides it:

expr : '-' expr %prec UMINUS   { $$ = createBinOp('u', $2, NULL); }

Conflicts

A shift/reduce conflict means the parser reached a point where it could either take another token or complete a rule, and one token of lookahead does not decide. Bison shifts, warns, and carries on. A reduce/reduce conflict means two rules could both be completed — nearly always a genuine grammar bug.

bison -d -v parser.y        # -v writes parser.output

Open parser.output and find the state named in the warning. It shows the items — productions with a dot marking how much has been seen — and exactly which two actions competed:

State 42

    stmt -> IF '(' expr ')' stmt .          [ELSE]
    stmt -> IF '(' expr ')' stmt . ELSE stmt

    ELSE  shift, and go to state 57
    ELSE  [reduce using rule 12 (stmt)]

The bracketed action is the one bison discarded. Learning to read this once saves an evening in Topic 5, where the dangling-else conflict arrives on schedule.

Zero conflicts should be the goal

Bison's defaults are often what you wanted, so a grammar with warnings can work perfectly. The problem is the next conflict — the one resolved the way you did not want — arriving in a report you have learned to ignore. Resolve them deliberately, with precedence declarations, and keep the count at zero.

Error recovery

error is a built-in token that matches wherever the parser is lost. An error production catches the mistake in a rule that knows what was being parsed, so it can say something useful:

assign : ID '=' expr ';'    { $$ = createAssign($1, $3); free($1); }
       | ID '=' expr error  { fprintf(stderr,
                                "line %d: missing ';' after assignment to '%s'\n",
                                yylineno, $1);
                              free($1); $$ = NULL; yyerrok; }
       ;

yyerrok tells bison to resume normal parsing rather than staying in error mode. Without it, the next few real errors are suppressed.

Debugging a parser

%define parse.trace          /* in the declarations section */

/* then, in main.c: */
extern int yydebug;
yydebug = 1;

This prints every shift, every reduce, and every state transition. It is verbose and it is the fastest way to find out why a particular input is not parsing the way you expect — you can watch the stack in the trace and compare it against the shift-reduce table in the Topic 2 notes.
