Topic 5 — Tree Search

Every method in this course so far learned a policy from experience. This one computes a decision at the moment it is needed, by looking ahead. We size the problem, build one search scaffold whose node ordering is a parameter rather than an algorithm, derive what α–β pruning buys and why it is exactly a square root, replace the evaluation function with random rollouts, derive UCT from the bandit bound of Topic 1, and finish where the line ends today: a learned evaluator inside the search loop, which is what search at inference time in a reasoning model is.

1. Game trees and the size of the problem

A two-player zero-sum game with perfect information is a tree. Nodes are positions, edges are legal moves, and the leaves carry the outcome from one player's point of view — say \(+1\), \(0\), \(-1\) for a win, draw, and loss for the player we call MAX. The two players alternate, MAX choosing the largest successor value and MIN the smallest. The value of a position is defined by the recursion

\[ V(s) \;=\; \begin{cases} u(s) & s \text{ terminal},\\[2pt] \max_{a \in \mathcal{A}(s)} V(\mathrm{do}(s,a)) & s \text{ a MAX node},\\[2pt] \min_{a \in \mathcal{A}(s)} V(\mathrm{do}(s,a)) & s \text{ a MIN node}. \end{cases} \]

This is the minimax value, and it is not an algorithm — it is a definition, with a two-line recursive evaluator that realises it. Zermelo's theorem says the recursion is well founded on any finite game: the value exists, and the optimal strategy for both players is to move to a successor achieving it. So in a formal sense every finite perfect-information game is solved. The entire subject exists because of the word finite.

Counting

Let \(b\) be the branching factor and \(d\) the depth. A complete tree of uniform branching factor has

\[ N(d) \;=\; \sum_{k=0}^{d} b^{k} \;=\; \frac{b^{\,d+1}-1}{b-1} \;\approx\; \frac{b}{b-1}\,b^{d}, \]

so up to a constant factor never larger than 2, the cost of exhaustive minimax is \(b^d\) — the leaves dominate everything above them. Two concrete games make the consequence vivid.

Tic-tac-toe. Nine cells, so a naive count of move orderings gives \(9! = 362\,880\). That number is an overcount in one respect and an undercount in another: games that end early are not \(9\) plies long, and distinct orderings are distinct tree paths whether or not they reach the same position. Enumerating the actual game tree from the empty board — stopping at every win and at every full board — gives 549 946 nodes, of which 255 168 are terminal, and the terminal count decomposes as 131 184 wins for X, 77 904 for O and 46 080 draws. Those are the numbers the search in §2 will reproduce exactly, because the tree is small enough to walk in a browser.

Connect Four. Seven columns, so \(b \approx 7\) until columns fill; forty-two cells, so \(d \le 42\). The naive bound \(7^{42} \approx 3.2 \times 10^{35}\) is a wild overestimate because it ignores full columns and terminal positions — the true count of legal, reachable positions is \(4\,531\,985\,219\,092 \approx 4.5 \times 10^{12}\). The game was solved in 1988. It is still, in 2026, entirely infeasible to enumerate inside an HTTP request.

Why "can we search this tree" is a budget question and not a correctness question. The minimax recursion is provably correct on both games, and the same eight lines of code run on both. What changes is only how long they take. This distinction is worth being pedantic about, because it determines what your engineering report is allowed to claim. If your agent plays badly, "the algorithm is wrong" is almost never the diagnosis; "the algorithm ran out of budget at depth 6 and the position it was scoring at depth 6 was misleading" is. It also determines what a fix looks like: correctness bugs are fixed by changing the recursion, budget failures are fixed by (i) visiting fewer nodes for the same answer, which is §2, (ii) spending the budget where it matters instead of uniformly, which is §3, or (iii) making each node worth more, which is §5. All three of those leave the definition of \(V(s)\) untouched.

The distinction the demo is built around, stated once in symbols. "Explores 30% of the nodes at each level" admits two readings and they are not close. Read as a per-level quota, the count is \(1 + f\sum_{k=1}^{d} b^k\): a constant factor \(f\), an unchanged exponent, and an infeasibility depth that moves by \(\log_b(1/f)\) — for \(b=7\) and \(f=0.3\), by less than one ply. Read as a per-node expansion rate, an unexpanded node takes its entire subtree with it, the surviving count at level \(k\) is \((fb)^k\), and the effective branching factor becomes \(fb\) — for \(b=7\) and \(f=0.3\) that is \(2.1\), which is a different problem. Every real pruning method is the second kind, because that is what pruning means: you decline to expand, not merely to score. When you compare your derivation against the node counts logged in games for DQ 2(d), the discrepancy you will find is almost always this one, plus transpositions the derivation does not model.

2. One scaffold, two orderings

It is conventional to present "exhaustive search" and "heuristic search" as two algorithms. They are not. They are one depth-limited recursion in which the sequence of children is produced by a callback, and the callback is the only thing that differs:

# search/scaffold.py — the whole of both "algorithms"
def search(state, player, depth, alpha, beta, order, ctr):
    ctr.nodes += 1
    if (u := state.terminal_value(player)) is not None: return u
    if depth == 0:                          return state.evaluate(player)
    best = -math.inf
    for m in order(state.legal_moves(), state, player):   # <-- the only difference
        v = -search(state.do(m), -player, depth - 1, -beta, -alpha, order, ctr)
        best = max(best, v); alpha = max(alpha, best)
        if alpha >= beta: break                # the cutoff; correctness proved below
    return best

identity  = lambda moves, s, p: moves                          # exhaustive evaluation
heuristic = lambda moves, s, p: sorted(moves, key=lambda m: -s.do(m).evaluate(p))

Both callbacks return a permutation of the same set. Neither can change which leaves exist, so neither can change \(V(s)\): the value returned is identical, and only the number of nodes entered differs. That is the claim you should be able to make about your own implementation, and it is a test you can write — run both orderings on a fixed set of positions and assert equality of the returned value, not merely of the chosen move.

Why the cutoff is safe

Carry two bounds down the recursion: \(\alpha\), the best value MAX is already assured of somewhere above, and \(\beta\), the best MIN is already assured of. At a MIN node whose running value has fallen to \(v \le \alpha\), MAX will never choose this node — a value at or above \(\alpha\) is already available on another line — so the remaining children can only lower \(v\) further and cannot change the root value. Cutting there discards subtrees whose values are irrelevant, not subtrees whose values are unknown. The consequence: α–β returns exactly the minimax value, and the pruned nodes are the ones that provably could not have mattered.

Why the best case is a square root

Ordering matters because a cutoff needs a good value early. Classify the nodes of the searched tree in the standard way. A PV node lies on the principal variation and must examine all \(b\) children: its first child is another PV node, the remaining \(b-1\) are CUT nodes. A CUT node is one where a cutoff will occur; under perfect ordering the refuting child is tried first, so it examines exactly one child, an ALL node. An ALL node has no cutoff available and examines all \(b\) children, each a CUT node. Writing \(C(k)\) and \(A(k)\) for the number of leaves under a CUT and ALL node of remaining depth \(k\):

\[ C(k) = A(k-1), \qquad A(k) = b\,C(k-1) \quad\Longrightarrow\quad C(k) = b\,C(k-2). \]

The recursion advances two plies for one factor of \(b\), so \(C(k) \asymp b^{k/2}\). Adding the principal variation gives the Knuth–Moore result exactly:

\[ N_{\text{leaves}}(d) \;=\; b^{\lceil d/2 \rceil} + b^{\lfloor d/2 \rfloor} - 1 \;\approx\; 2\,b^{d/2} \;=\; 2\left(\sqrt{b}\right)^{d}. \]

The effective branching factor is \(\sqrt{b}\). Read the identity the other way and it says something more useful than a complexity class: for a fixed leaf budget \(B\), exhaustive search reaches depth \(\log_b B\) and perfectly ordered α–β reaches \(2\log_b B\). Perfect ordering doubles the reachable depth at the same cost. In practice ordering is imperfect and the realised effective branching factor lies between \(\sqrt{b}\) and \(b\); the ratio of the two node counts you log is the honest measurement of how good your ordering heuristic actually is.

Why the ordering callback is a parameter and not two files. Three arguments, in increasing order of how much they will cost you if ignored. First, the equality test above is only meaningful if there is one recursion: if exhaustive and heuristic search are separate implementations, a discrepancy between them is ambiguous — either the ordering is wrong or one of the two searches is — and you will spend an evening finding out which. Second, the node counts become directly comparable, because they are counts of the same event in the same function; a table comparing nodes_expanded across two implementations is comparing two definitions of a node as much as two strategies. Third, the ordering callback is the natural place for every later improvement — killer moves, iterative deepening's previous-best-move, and in §5 a policy network's prior — none of which is a new algorithm either. The syllabus consolidates five required implementations to three for exactly this reason: two of the five were the same code.

3. Monte Carlo tree search: the four phases

α–β solves the budget problem in one direction: it gets the same answer for fewer nodes. It does not solve the other one. A depth-limited search must call evaluate() at its frontier, and the quality of the move it returns is bounded by the quality of that function. For chess a material-plus-mobility evaluation is serviceable enough that depth was the binding constraint for forty years. For Go it was not: \(b \approx 250\), \(d \approx 150\), and — the part that actually blocked progress — no hand-written function that reliably ranks two Go positions. Deeper search over a bad evaluation returns a confidently wrong answer.

Monte Carlo tree search removes the evaluation function and replaces it with a statistic. The value of a position is estimated by playing the game out at random from it, many times, and averaging the results. Random play is a terrible policy; the estimator is nonetheless informative, because it is applied to every candidate equally and what is being compared is the difference between two positions under a common measurement. And it requires no domain knowledge beyond the rules and the terminal score, which is precisely the knowledge that was missing.

The tree is grown asymmetrically, one node per iteration, and each iteration is four phases:

  1. Selection. From the root, descend by a tree policy — UCT in §4 — while the current node is fully expanded, until reaching a node with an untried move or a terminal position.
  2. Expansion. Add one child for one untried move. This is the only place the tree grows, which is why the node count equals the iteration count plus one.
  3. Simulation. From the new child, play to termination under a default policy — uniformly random in the base algorithm — and record the outcome. Nothing here is stored.
  4. Backpropagation. Walk from the new child to the root, incrementing each node's visit count \(N_i\) and adding the outcome to \(W_i\), scored from the point of view of the player who moved into that node.

Two properties follow immediately and are worth naming. MCTS is anytime: the tree after \(n\) iterations is a valid, usable estimate for every \(n\), so a wall-clock or node budget can be enforced by stopping, with no partial-search artefact to repair. And it is asymmetric: iterations concentrate where the tree policy sends them, so the tree is deep along promising lines and one node thick elsewhere, which is the opposite of the uniform frontier a depth-limited search produces.

The sign convention that causes most MCTS bugs. \(W_i\) must be scored for the player who made the move into node \(i\), not for the player to move at \(i\) and not for the root player. Get it wrong and the search maximises the opponent's win rate at every other ply; the agent will look like it is working, because it still beats random play, and it will lose every won position. The test that catches it is not a win-rate test — construct a position with a forced win in one, run 200 iterations, and assert the chosen move is the winning move.

4. UCT, derived from UCB

Selection is a bandit problem, and Topic 1 already solved it. At a node with \(N\) visits whose children have \(W_i\) accumulated wins over \(N_i\) visits, treat each child as an arm with unknown mean \(\mu_i\) and empirical mean \(\hat\mu_i = W_i/N_i\). Hoeffding's inequality bounds the deviation of an average of \(N_i\) bounded samples,

\[ \Pr\!\left( \mu_i \ge \hat\mu_i + \varepsilon \right) \;\le\; \exp\!\left(-2 N_i \varepsilon^2\right), \]

and setting the right-hand side to \(N^{-4}\) — a failure probability that shrinks fast enough for the union bound over all arms and all steps to remain summable — gives \(\varepsilon = \sqrt{2\ln N / N_i}\). Adding that radius to the empirical mean is optimism under uncertainty, and it is the UCB1 rule of Topic 1 with \(t\) replaced by the parent's visit count. Applying it recursively at every node of a tree is UCT:

\[ \mathrm{UCT}_i \;=\; \underbrace{\frac{W_i}{N_i}}_{\text{exploitation}} \;+\; C\underbrace{\sqrt{\frac{\ln N}{N_i}}}_{\text{exploration}}, \qquad N = \sum_j N_j . \]

\(C = \sqrt{2}\) is the constant the derivation produces when rewards lie in \([0,1]\); it is not sacred, because the derivation assumes independent samples from a stationary distribution and the samples at an internal node of a growing tree are neither. The regret guarantee inherited from the bandit analysis is what makes the rule the right starting point: the number of pulls of a suboptimal arm is \(O(\ln N)\), so the probability of selecting a suboptimal move at the root converges to zero, and UCT's value estimates converge to the minimax value as \(N \to \infty\).

When exploration dominates (DQ 1c)

Set the two terms against each other. Exploration dominates when

\[ C\sqrt{\frac{\ln N}{N_i}} \;>\; \frac{W_i}{N_i} \;\Longleftrightarrow\; C\sqrt{\ln N}\,\sqrt{N_i} \;>\; W_i \;\Longleftrightarrow\; \boxed{\,N_i \;>\; \frac{W_i^{2}}{C^{2}\ln N}\,} \]

after multiplying both sides by \(N_i > 0\). Both terms decay in \(N_i\), but at different rates — \(N_i^{-1}\) against \(N_i^{-1/2}\) — so the exploitation term is the one that vanishes first and exploration dominates for large \(N_i\), not small. At the DQ 1 parameters \(W_i = 10\), \(N = 1000\), \(C = \sqrt{2}\), the crossing sits at \(N_i^\star = 100/(2\ln 1000) = 7.24\). Note where that falls: a node with \(W_i = 10\) must have \(N_i \ge 10\), so over the entire physically realisable range the exploration term is already the larger one. That is a statement about the DQ's parameters, not about UCT in general — a node with \(W_i = 10\) out of \(N_i = 10\) has an implausibly perfect record and a correspondingly small visit count.

The reason low-visit nodes are prioritised early is a separate and simpler fact: \(W_i/N_i\) is confined to \([0,1]\), while \(C\sqrt{\ln N/N_i} \to \infty\) as \(N_i \to 0\). An unvisited child has infinite priority and is taken immediately, so every child is tried once before any is tried twice; among children with comparable win rates the less-visited one always wins the comparison. Exploration is therefore front-loaded by construction and decays as \(1/\sqrt{N_i}\) thereafter.

Why \(C\) is problem-dependent, and the one-line heuristic that actually works (DQ 4c). The bound \(\varepsilon = \sqrt{2\ln N/N_i}\) is derived for rewards in \([0,1]\). Nothing else in the derivation carries scale information, so \(C\) is doing the job of a units conversion between the reward range and the confidence radius: if outcomes are scored \(\{-1,0,1\}\) instead of \(\{0,\tfrac12,1\}\) the appropriate \(C\) doubles, and no amount of tuning on the wrong scale recovers it. Beyond units, \(C\) is trading the variance of the rollout estimator against the cost of a wrong commitment — noisy rollouts and near-tied moves both call for larger \(C\). The practical heuristic is not a formula but a protocol: fix the iteration budget, sweep \(C \in \{0.1, 0.5, 1, \sqrt2, 2\}\) against a fixed reference opponent, and take the peak; then check that the peak is not at a boundary, because a peak at the edge of the sweep means the reward scale, not \(C\), is what needs fixing. Report the sweep, not the winner — a flat curve and a sharp curve carry very different information about how much your result depends on the constant.

5. Learning the evaluation: AlphaZero and MuZero

The random rollout was a device for getting a value estimate without a value function. It works, and it is enormously wasteful: a full playout costs \(O(d)\) moves to produce one bounded sample of the outcome, and the information in it is discarded except for a single increment. Replace it with a function that returns an estimate of the same quantity in one forward pass, and the iteration cost collapses.

AlphaZero is that substitution, done with a network trained by self-play. A single network \(f_\theta(s) = (\mathbf{p}, v)\) outputs a prior over moves and a scalar value in \([-1,1]\). MCTS uses both: the value replaces the rollout, and the prior enters the selection rule, which becomes PUCT:

\[ a^\star = \arg\max_a \left[ Q(s,a) \;+\; c_{\text{puct}}\, P(s,a)\, \frac{\sqrt{\sum_b N(s,b)}}{1 + N(s,a)} \right]. \]

Three changes from UCT, each with a reason. The prior \(P(s,a)\) multiplies the exploration bonus, so a move the network considers implausible is not visited merely because it is unvisited — this is what makes \(b \approx 250\) tractable, since the pruning happens at selection time rather than after a wasted rollout. The numerator is \(\sqrt{N}\) rather than \(\sqrt{\ln N}\), a polynomial rather than logarithmic schedule, which explores more persistently; the logarithm's justification was an asymptotic regret bound, and a search running a few hundred simulations is nowhere near asymptopia. And the denominator is \(1 + N(s,a)\) rather than \(N(s,a)\), which keeps the bonus finite at zero visits so the prior alone breaks the first-visit tie.

Training closes the loop. Each self-play move records the search's visit distribution \(\boldsymbol{\pi} \propto N(s,\cdot)^{1/\tau}\) and, at the end, the game outcome \(z\). The network is fit to both:

\[ \mathcal{L}(\theta) \;=\; (z - v_\theta)^2 \;-\; \boldsymbol{\pi}^\top \log \mathbf{p}_\theta \;+\; \lambda \lVert\theta\rVert^2. \]

The first term is regression onto the realised outcome; the second is a cross-entropy that distils the search into the network. That second term is the engine: MCTS with the current network is stronger than the network alone, so \(\boldsymbol{\pi}\) is a better policy than \(\mathbf{p}_\theta\), and training toward it is policy improvement with the search operator playing the role the \(\max\) plays in value iteration. The improved network makes the next search stronger still. This is the same policy-iteration structure as Topic 1, with a tree search substituted for the greedy step.

What MuZero learns that AlphaZero is given (DQ 6c)

AlphaZero is handed a simulator: given \(s\) and \(a\) it can compute the successor exactly, which is what lets it build a tree at all. MuZero removes that assumption and learns three functions instead:

\[ s^0 = h_\theta(o_{1:t}), \qquad (r^k, s^k) = g_\theta(s^{k-1}, a^k), \qquad (\mathbf{p}^k, v^k) = f_\theta(s^k). \]

The representation \(h\) maps observations to a latent state, the dynamics \(g\) advances the latent state under an action and predicts the immediate reward, and the prediction head \(f\) supplies the policy and value that PUCT needs. The search runs entirely inside the latent space: no board is ever reconstructed, and the rules are never written down.

The point that repays attention is what these functions are trained to do. The loss constrains only three observable quantities — the predicted reward against the reward actually received, the predicted policy against the search's visit distribution, and the predicted value against the \(n\)-step bootstrapped return:

\[ \mathcal{L} = \sum_{k=0}^{K}\Big[ \ell^{r}(u_{t+k},\, r^k_t) + \ell^{p}(\boldsymbol{\pi}_{t+k},\, \mathbf{p}^k_t) + \ell^{v}(z_{t+k},\, v^k_t) \Big] + \lambda\lVert\theta\rVert^2 . \]

There is no term requiring \(s^k\) to decode back to a real position, and none requiring \(g\) to be a correct transition function. The latent state is therefore under-determined by design: it need only preserve the information that reward, value and policy depend on, and it is free to discard everything else. That is the mathematical content of "infers an optimal policy without knowing the rules." MuZero does not learn the rules and then plan; it learns whatever abstraction makes planning produce correct values, which is a strictly weaker and strictly cheaper requirement. The cost is that its model is only trustworthy on the distribution it was trained on and cannot be inspected, queried, or reused for anything but this search.

Why this is the antecedent of search at inference time, and where the analogy is load-bearing. The structural claim of this topic is that AlphaZero's loop — propose with a policy, evaluate with a learned value, search over the proposals, then train the policy on what the search found — is the same loop a reasoning model runs when it samples multiple candidate continuations, scores them with a learned verifier or reward model, and is subsequently trained on the ones that scored well. The correspondence is exact at three points: the prior \(P(s,a)\) is the base model's next-token or next-step distribution, the value \(v_\theta\) is the verifier, and the distillation term \(-\boldsymbol{\pi}^\top\log\mathbf{p}_\theta\) is the rejection-sampling or preference-training step that folds search results back into weights. It is not exact in one place that matters: a game has a terminal outcome \(z\) that is free, objective, and unarguable, and open-ended reasoning does not. Every difficulty in Topic 6 descends from having to learn that \(z\) from human comparisons instead of reading it off the board — which is why the reward-hacking evidence you will gather there has no analogue here.

6. Benchmarking search honestly

Four measurements, each answering a different question, and none of them substitutable for another.

  • Nodes expanded. The implementation-independent measure of work. It is the right axis for comparing search strategies, because it does not move when you change language, machine, or optimisation level. It is the wrong axis for a deployment decision, because it prices every node identically and a PUCT node carrying a network forward pass costs thousands of times a random-rollout node.
  • Wall-clock per move. The only measurement the deployment actually feels, and the only one that catches the cost hidden inside a node. Report it alongside nodes, never instead: the ratio between them is the per-node cost, and a revision that improves one while worsening the ratio is worth knowing about.
  • Decision quality. Win rate against a fixed reference opponent, over enough games for the interval to mean something.
  • Scalability. How each of the above moves as depth, iteration budget, or board size grows. A single operating point cannot distinguish a method that is better here from one that is better everywhere, and the second claim is the one worth making.

Why the reference opponent must be fixed

The tempting alternative is the round-robin win-rate matrix on its own: play every agent against every other and rank by total score. It has two defects and the second is fatal. The first is that the numbers are not on a common scale — agent A beating agent B 60% of the time and agent B beating agent C 55% of the time places no constraint at all on A against C, because the two figures were measured against different opponents. The second is that game agents are frequently non-transitive: A beats B, B beats C, and C beats A is a stable and common configuration, produced whenever agents exploit each other's specific blind spots rather than differing in general strength. A cycle has no ordering, so "which agent is stronger" has no answer of the form the matrix is being asked for.

A fixed reference opponent removes both defects by construction. Every agent is measured against the same distribution of positions and the same errors, so the scores are comparable by definition; and because the reference never changes, a score computed today is comparable with one computed after a revision. Two conditions on the reference: it must be strong enough that your agents do not all score 100% and weak enough that they do not all score 0%, since a saturated metric has no resolution; and it must be frozen, versioned, and stored — a "random opponent" reseeded differently between runs is not a fixed reference. Keep the round-robin matrix as well. It answers a genuinely different question — whether any pair is non-transitive — and if it is, that is a finding to report, not a nuisance to average away.

Why a revision that makes one metric worse can still be the right revision. Adding move ordering to your α–β search will cut nodes_expanded by a large factor and may well increase wall-clock per move, because the ordering callback evaluates every child before the recursion does. Both numbers are correct and the trade is real. What makes it acceptable is that it is stated: "ordering reduced nodes expanded at depth 6 from 18 296 to 5 573, a factor of 3.3, and increased median move time from 41 ms to 55 ms; we take the trade because the node budget, not the clock, is what bounds us at depth 8 and above, where the ratio inverts." That sentence is defensible and a reader can disagree with it on the evidence. What is not acceptable is reporting only the node count. The requirement in the build step is not that your revision be a Pareto improvement — most interesting revisions are not — but that you name the axis you gave up, quantify what it cost, and say why the exchange is favourable for the operating point you are deploying at.

7. In practice (Search Arena)

In the build. Three agents behind one POST /act: the shared scaffold under both orderings, MCTS with a configurable \(C\), and the AlphaZero-inspired agent whose evaluation network is trained in train/ and exported to a NumPy archive for serving like every other policy in this course. Nothing in the serving tier imports PyTorch; a policy/value head is a handful of matrix multiplies, and the standing tests/test_no_torch.py guard still applies. Every game written by the harness lands in games, and every number in your report is a query against it — including the node counts you compare with your DQ 2 derivation.

games.movesintgame length; separates "won fast" from "won at all", and detects a search that is timing out into random play

Two hundred games per pairing is not a round number chosen for comfort. At a true win rate near \(0.5\) the standard error of a proportion over \(n\) games is \(\sqrt{p(1-p)/n} = 0.035\) at \(n=200\), so the 95% interval is about \(\pm 7\) points; a 5-point difference measured over 50 games is indistinguishable from nothing.

The node budget, and why it must appear in the response

A depth-limited search whose depth is chosen by the caller is an unbounded compute request wearing a small integer. At \(b=7\), depth 8 is \(\sum_{k \le 8} 7^k \approx 6.7\) million nodes; the free-tier instance will exhaust its memory or its request timeout, and the failure will present as a dead worker rather than as an error the caller can act on. The budget is enforced inside the scaffold, where the node counter already lives, and the amount consumed is returned in the response body — because a caller that receives a move with no indication that the search was truncated has been given a silently degraded answer:

# search/scaffold.py — the same recursion as §2, with the two additions
class BudgetExceeded(Exception): pass

def search(state, player, depth, alpha, beta, order, ctr):
    ctr.nodes += 1
    if ctr.nodes > ctr.budget: raise BudgetExceeded          # 1. checked at entry, not at the leaves
    if (u := state.terminal_value(player)) is not None: return u
    if depth == 0:                          return state.evaluate(player)
    best = -math.inf
    for m in order(state.legal_moves(), state, player):
        v = -search(state.do(m), -player, depth - 1, -beta, -alpha, order, ctr)
        best = max(best, v); alpha = max(alpha, best)
        if alpha >= beta: break
    return best

# api/act.py — iterative deepening makes the budget safe to hit
def act(state, player, max_depth, budget=200_000):
    ctr = Counter(nodes=0, budget=budget)
    move, reached = state.legal_moves()[0], 0
    for d in range(1, max_depth + 1):                             # 2. every depth leaves a usable move
        try:
            move = best_move(state, player, d, heuristic, ctr); reached = d
        except BudgetExceeded:
            break                                                # keep the last completed depth
    return {"move": move, "nodes_expanded": ctr.nodes, "budget": budget,
            "depth_reached": reached, "truncated": ctr.nodes >= budget}

Iterative deepening is what makes the guard usable rather than merely safe. Raising the exception mid-search discards that depth's work, so without an outer loop a truncated request has no answer at all; with one, the last completed depth is always available and the response can report which depth that was. The re-search cost is small for the reason §2 gives — the tree at depth \(d\) is \(b\) times the tree at \(d-1\), so every earlier iteration together costs a \(1/(b-1)\) fraction of the last — and the previous iteration's best move is the best ordering hint available, which usually more than repays it. MCTS needs none of this: it is anytime already, and its budget is a loop bound.

The test that makes the budget real. A budget that is never hit in testing is a constant, not a guard. The build step asks for a node-budget enforcement test, and the useful form of it is a request at a depth whose node count you have computed to exceed the budget, asserting three things: the response is a 200 and not a 500, truncated is true, and depth_reached is strictly less than the depth requested. Assert the returned move is legal too — the failure mode where truncation returns the placeholder first legal move is correct behaviour, but a placeholder that is stale from a previous position is not.
What carries forward. The bandit bound of Topic 1 became the selection rule of §4 without modification, and the exploration constant is the same knob under a third name. The policy-improvement loop of §5 is value iteration with a tree search in place of the \(\max\), and it is the last place in this course where the target of improvement is available for free. Topic 6 removes that: the outcome \(z\) that a game hands you at no cost has to be learned from human comparisons, and the search-then-distil loop becomes sample-then-score-then-train. When you read that MCTS is the direct antecedent of search at inference time in a reasoning model, the claim is this specific one — the loop is the same loop, and only the source of the value signal has changed.
