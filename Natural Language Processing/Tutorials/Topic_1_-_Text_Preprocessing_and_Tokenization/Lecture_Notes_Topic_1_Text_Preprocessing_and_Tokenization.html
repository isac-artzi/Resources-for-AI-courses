Topic 1 — Text Preprocessing and Tokenization

How raw text becomes a sequence of integers: normalization, the classical cleaning pipeline, the three granularities, and the subword algorithms (BPE and WordPiece) that every transformer model depends on.

What you should walk away with. (1) A precise definition of a token, and the ability to say what any given tokenizer will do to a string before you run it. (2) Fluency with the classical pipeline — normalization, punctuation, stop words, stemming, lemmatization — and with the specific damage each step can do. (3) The ability to run Byte-Pair Encoding by hand on a small corpus, in the right merge order. (4) An understanding of WordPiece and how it differs from BPE at training time and at encoding time. (5) The vocabulary-size trade-off expressed numerically: out-of-vocabulary rate on one side, pieces per word and sequence length on the other. (6) A working answer to "why does a transformer tokenize this way and not some other way", and a short list of measurements to run instead of staring at an OOV rate that is always near zero.

1 · What tokenization actually decides interactive

A model never sees text. It sees a list of integers. Tokenization is the function that turns a string into that list, and detokenization is the function that turns the list back into a string. Everything in this topic is about choosing that function well.

Three decisions are baked into every tokenizer, and they are the decisions you are actually making when you pick one off the shelf:

  1. The symbol inventory — the finite set of pieces the tokenizer is allowed to emit. Call its size V. This fixes the size of the embedding matrix and of the output softmax.
  2. The segmentation rule — given a string and the inventory, which sequence of pieces do you produce? Greedy longest match, learned merge order, and probabilistic segmentation all give different answers from the same inventory.
  3. What happens to anything not covered — an [UNK] token, a byte fallback, or a crash. This is the difference between a tokenizer that is total (defined on every possible input) and one that is not.

Those three decisions produce a fourth quantity you will care about constantly: how many pieces per word the tokenizer emits, often called fertility. Fertility sets sequence length, sequence length sets attention cost, and attention cost sets your bill.

The classical dividing line is granularity. Word level treats the space-and-punctuation-delimited word as the unit. Character level treats each character as the unit. Subword sits between them, learning its units from a corpus. The demo below runs all three on whatever you type.

The one-sentence version. Word level buys short sequences with a huge vocabulary and a hole for every unseen word; character level buys a tiny vocabulary and no holes with very long sequences; subword buys a modest vocabulary, no holes, and sequences only slightly longer than word level. That is why subword won.

2 · Normalization: case, Unicode, numbers

Normalization runs before segmentation. It decides which surface strings should be treated as the same string. Every normalization step is a deliberate loss of information, traded for a reduction in vocabulary size and data sparsity.

Case folding

The, the, and THE are three distinct types until you lowercase them, and one type afterwards. For sentiment classification on informal text this is almost always the right call. For named entity recognition it is almost always wrong: Apple and apple, US and us, Turkey and turkey are the distinctions the task is about. Note also that lowercasing is not the same operation as Unicode case folding — "STRASSE".toLowerCase() gives strasse, which will never match straße.

Unicode normalization

The same visible character can have more than one byte representation. The character é can be a single code point U+00E9, or the two code points e + U+0301 (combining acute accent). They render identically and compare unequal. The Unicode normalization forms fix this:

  • NFC composes: e + combining accent becomes the single code point. This is the sane default for stored text.
  • NFD decomposes: the single code point becomes base letter plus combining mark. Useful if the next step is to strip accents, because you can then drop every combining mark.
  • NFKC / NFKD additionally apply compatibility mappings: the ligature ﬁ becomes fi, full-width Latin letters become ASCII, superscript ² becomes 2. Aggressive, and lossy in ways that occasionally matter.

If you never call a normalization function, you have still made a choice — you have chosen "whatever form the upstream system happened to emit", which is not stable across sources. Pick one form, apply it at ingest, and record which one in your model card.

Accent stripping

NFD followed by removing the combining marks turns café into cafe and naïve into naive. Useful for matching sloppy user input against a clean catalogue. Destructive in French, Spanish, Vietnamese and many other languages where the accent is not decoration: in Spanish si is "if" and sí is "yes".

Numbers, dates, and other high-cardinality junk

Every distinct number in a corpus is a distinct type, and almost all of them occur once. Three common policies:

  • Keep them. Correct when the magnitude matters (financial text, product specifications).
  • Replace with a placeholder. 3.5% becomes <NUM>%. Collapses thousands of singleton types into one and helps a small classifier generalize.
  • Bucket them. <NUM_SMALL>, <NUM_YEAR>, <NUM_MONEY>. More work, keeps more signal.

Note that modern subword tokenizers handle numbers by fragmenting them into digit pieces, which is why arithmetic is awkward for language models: 1234 may be a single piece in one tokenizer and 12 + 34 in another, and the model has to learn place value across an inconsistent segmentation.

3 · The classical cleaning pipeline interactive

The classical pipeline is a sequence of filters applied to a list of word tokens. It predates neural models and it is still the right tool when your downstream model is a bag-of-words classifier, a topic model, or a keyword index — anything that treats the document as an unordered multiset and has no way to learn that the is uninformative.

raw text
  → normalize        (case fold, Unicode form, accents)
  → segment          (whitespace + punctuation rules)
  → filter           (drop punctuation, digits, stop words)
  → conflate         (stem or lemmatize)
  → token list

Punctuation

Dropping punctuation removes tokens that a bag-of-words model cannot use. It also removes sentence boundaries, the difference between a question and a statement, and the apostrophe that holds a contraction together. Strip punctuation inside tokens and don't becomes dont (recoverable) or don + t (not recoverable).

Stop words

A stop list is a hand-written set of high-frequency, low-content words. Removing them shrinks the index and speeds up classical models. Two facts about stop lists that people learn the hard way:

  • Standard English stop lists contain negations. not, no, nor are on most of them. After stop-word removal, "the service was not good" and "the service was good" are the same document. If your task is sentiment, this is a defect you introduced yourself.
  • Stop lists are language- and domain-specific. An English list applied to Spanish text removes nothing useful. A general list applied to legal text leaves shall and hereinafter in place while removing against, which is a content word in that domain.

For a transformer, you do not remove stop words at all. The model has attention; it can learn to ignore what it should ignore, and function words carry syntax the model uses. Stop-word removal is a classical-pipeline tool, not a preprocessing universal.

4 · Stemming vs lemmatization interactive

Both operations conflate inflected forms so that run, runs and running land on the same index. They differ in method, in cost, and in what they guarantee.

StemmingLemmatization
MethodSuffix-stripping rules applied in a fixed orderDictionary lookup plus morphological analysis, usually with the part of speech
OutputA truncated string, not required to be a wordA real dictionary form (the lemma)
Needs POS?NoUsually yes — saw is see as a verb, saw as a noun
CostMicroseconds, no data filesSlower, needs a lexicon and often a tagger
Failure modeOver-stemming (two meanings collide) and under-stemming (one meaning splits)Silently returns the input when the word is not in the lexicon
Typical useSearch indexes, fast classical classifiersLinguistic analysis, when the output is shown to a person

Two named failure modes worth being able to describe:

  • Over-stemming. caring loses -ing and becomes car. It now shares an index with the vehicle. Two unrelated meanings merged.
  • Under-stemming. ran and running do not reduce to the same string under any suffix rule, because ran is irregular. One meaning stayed split.

Demo · Stem and lemma, side by side, on words you supply

The stemmer is a real suffix-stripping cascade (Porter-style rules, longest suffix first, with a doubled-consonant fix). The lemmatizer is a small dictionary plus a few plural rules. Neither is production grade — the point is to see where they disagree.

Read the rows where the two columns disagree. better stems to bet — the rule sees a comparative -er, strips it, and the doubled-consonant fix finishes the job. The lemma is good, which no suffix rule could ever produce. Conversely tokenization stems cleanly to tokenize while a dictionary lemmatizer that has not been told about -ization leaves it alone.

Trap. Stemming or lemmatizing before a subword tokenizer is close to pointless and often harmful. The subword vocabulary already contains ##ing and ##s as pieces, so the model sees the shared stem piece anyway — and by mangling the surface form first you hand the tokenizer strings that never appeared in its training corpus, which raises the piece count. Classical conflation belongs in classical pipelines.

6 · Word level and the OOV wall mathinteractive

Word-level tokenization takes the V most frequent words of a training corpus as the vocabulary and maps everything else to a single [UNK] token. The failure is structural, and two empirical regularities explain it.

Zipf's law. Rank the types of a corpus by frequency. The frequency of the type at rank r falls roughly as a power law:

f(r) ≈ C · r−a, with a near 1 for natural language

The consequence is a very long tail: a large share of the distinct words in any corpus occur exactly once. Those hapax legomena are not noise you can discard — they are names, places, numbers, typos, and the new words that appear every day.

Heaps' law. The number of distinct types seen after reading N tokens grows without bound:

|V(N)| ≈ k · Nβ, with β usually reported between about 0.4 and 0.6

Because β is positive, there is no corpus size at which the vocabulary stops growing. A fixed word list is therefore always incomplete on tomorrow's data, no matter how much text you read today.

Defining the rate. Two different numbers both get called "OOV rate", and mixing them up makes results incomparable:

OOVtoken(V) = (Σr > V f(r)) / (Σr f(r)) — share of running text that is unknown
OOVtype(V) = (T − V) / T — share of the distinct word list that is unknown

The type rate is always the more alarming of the two, because the tail is mostly singletons. The token rate is the one that predicts how often a user actually sees an [UNK]. State which one you are reporting.

Demo · Vocabulary size against OOV rate — drag the curve

Drag anywhere on the plot, or use the sliders. Frequencies come from a Zipf model with T = 30,000 types and the exponent you choose — this is a model of a corpus, not a measurement of one, so read the shape rather than the third decimal place.

Drag toward the left edge and watch the curve go vertical. That steepness is the whole problem with word-level vocabularies: halving the vocabulary from 30,000 to 15,000 costs you little, and halving it again from 2,000 to 1,000 costs you a great deal. To push the token OOV rate below a percent or so you need a vocabulary large enough that the embedding matrix dominates your parameter count, and the rarest rows in it will have been updated a handful of times during training.

What an [UNK] costs. It is not a small error. Every unknown word collapses to one identical vector, so an unknown drug name, an unknown company and an unknown misspelling are indistinguishable to the model. In a generation task the model can emit [UNK], and there is no way to turn it back into text. Subword tokenization exists to make this token unnecessary.

7 · Character level: the other extreme math

Take the vocabulary down to the set of characters — a few hundred symbols for Latin script, 256 if you work in raw bytes. The properties invert:

Word levelCharacter level
Vocabulary size50k – 500k+~100 – 256
Sequence length for one sentenceshortest possibleroughly 4–6× longer
OOVstructural, unavoidablenone, by construction
Embedding matrixdominates parameter countnegligible
Morphologyinvisible — run and running are unrelated idsfully visible, but must be learned from scratch
Attention cost per sentencebaseline~16–36× baseline (quadratic in length)

That last row is the killer. Self-attention costs O(L²) in sequence length L. Making sequences five times longer makes attention roughly twenty-five times more expensive, and it also means a fixed context window holds five times less text. Character models are trained and they work; they are not the default because the compute goes to modelling spelling rather than meaning.

The obvious question is whether there is a setting between "one unit per word" and "one unit per character" that keeps the open vocabulary of the character model and most of the sequence length of the word model. There is, and you can learn it from data.

8 · Byte-Pair Encoding, by hand math

Byte-Pair Encoding was a data-compression algorithm before it was a tokenizer: repeatedly replace the most frequent pair of adjacent symbols with a new symbol. Sennrich, Haddow and Birch adapted it to open-vocabulary machine translation in 2016, and it is now the training procedure behind most production tokenizers.

The training loop

1. Split the corpus into words with counts.
2. Represent each word as a sequence of characters, with an
   end-of-word marker so that word-final pieces stay distinct.
3. Count every adjacent symbol pair, weighting by word count.
4. Merge the most frequent pair everywhere; the merged string
   becomes a new symbol and the merge is appended to an ordered list.
5. Repeat from 3 until the vocabulary reaches the target size.

Two details decide whether your run is reproducible. First, the end-of-word marker (written _ here): without it, the er in newer and the er in tremendous are the same symbol, and the tokenizer cannot represent "this piece ends a word". Second, the tie-break rule: when two pairs have the same count you must break the tie deterministically or two training runs on identical data will produce different vocabularies. The rule used here and in the widget below is earliest first occurrence in a left-to-right scan of the corpus.

The worked example

Corpus, already segmented into words with counts, each word written as characters plus the end-of-word marker:

3 × w i d e r _
2 × n e w _

Three observations that generalize to a real run over billions of words:

  • The frequent words low and newer ended as single symbols. Frequent words become whole tokens for free — nobody put them in a list.
  • The rare word widest stayed almost entirely in characters. Rare words pay in pieces, which is exactly the trade you want.
  • The output is an ordered list. The order is part of the model. Apply the same merges in a different order and you get a different segmentation.

10 · Encoding new text with learned merges interactive

Training produced an ordered merge list. Encoding a new string is a separate procedure and people routinely get it wrong: you do not search for the longest piece in the vocabulary. You split the word into characters and then apply the learned merges in the order they were learned, applying each one everywhere it matches before moving to the next.

def encode(word, merges):
    symbols = list(word) + ["_"]
    for (a, b) in merges:               # learned order matters
        i = 0
        out = []
        while i < len(symbols):
            if i + 1 < len(symbols) and symbols[i] == a and symbols[i+1] == b:
                out.append(a + b)
                i += 2
            else:
                out.append(symbols[i])
                i += 1
        symbols = out
    return symbols

Demo · Apply the eight learned merges to any word

Type a word. Every merge rule is shown in learned order with the state after it, and rules that did not match are marked. Try lower (never seen in training), newest, widest, slow.

lower never appeared in the training corpus, and the tokenizer still produces two clean pieces, low + er_, both of which the model has seen thousands of times in other contexts. That is the entire promise of subword tokenization: an unseen word is represented by seen parts, in a way that preserves its relationship to low and to newer.

Now try widest. Not one of the eight rules matches it, so the word stays as seven raw symbols. Nothing is lost — the string still round-trips exactly — but it costs seven tokens instead of one. This is what "rare words pay in pieces" means in practice, and the piece count is the number to watch when a domain shifts under you.

11 · WordPiece math

WordPiece is the tokenizer used by BERT and its relatives. It comes from Schuster and Nakajima's 2012 work on Japanese and Korean voice search and it differs from BPE in two places.

Difference 1 — the training criterion

BPE merges the pair that occurs most often. WordPiece merges the pair whose merge most increases the likelihood of the training data under a unigram language model over pieces. In practice the selection score is

score(a, b) = count(ab) / (count(a) · count(b))

Read the denominator. A pair of two very frequent pieces has to be extremely frequent together to win, because you would already have predicted the pieces individually. This biases the vocabulary toward pieces that genuinely belong together — morphemes rather than accidents of co-occurrence. Frequency alone would merge th early because t and h are both common; the normalized score is much less impressed by that.

Difference 2 — the encoding procedure

WordPiece does not replay a merge list. It performs greedy longest-match-first segmentation: at the current position take the longest string that is in the vocabulary, emit it, advance, and prefix every non-initial piece with ##. If no piece matches at some position, the whole word becomes [UNK] — WordPiece has a genuine unknown token, unlike byte-level BPE.

vocabulary contains: token, ##ize, ##r, ##s, ##ation, un, ##happy, ##ness

"tokenizers" → token + ##ize + ##r + ##s
"tokenization" → token + ##ization        (if ##ization is in the vocabulary)
"unhappiness"  → un + ##happy + ##ness

The ## prefix is not decoration. It is what makes detokenization unambiguous: pieces carrying ## are concatenated onto the previous piece, pieces without it start a new word preceded by a space.

These are engineering differences, not a hierarchy. All three give you an open vocabulary with a fixed symbol set; they disagree about which pieces are worth having and how to choose among segmentations.

12 · Byte-level BPE, SentencePiece, and special tokens

Byte-level BPE

Ordinary BPE starts from the set of characters observed in the training corpus. Feed it a character it never saw — a Cyrillic letter, a rare emoji, a mathematical symbol — and it has no symbol for it. Byte-level BPE starts from the 256 possible byte values instead. Since any Unicode string has a UTF-8 byte encoding, and every byte is in the vocabulary, every possible input is representable. The GPT-2 tokenizer works this way, which is why it has no [UNK] token at all.

The cost is paid by non-Latin scripts: one character of Latin text is one byte, one character of Chinese or Devanagari is three, so the same sentence costs several times more tokens in some languages than in others. That is a real fairness and cost issue, not a footnote — the same context window holds far less text, and per-token pricing charges more, for exactly the languages that are already underserved.

SentencePiece and the pre-tokenization question

Everything above assumed you could split text into words before learning subwords. Chinese, Japanese, Thai and others are not written with spaces, so "split on whitespace first" is not available. SentencePiece treats the raw string, spaces included, as the input: the space is replaced with a visible marker (commonly ▁) and becomes an ordinary character that merges can consume. Two consequences: the pipeline is language-agnostic, and detokenization is exact — replace the marker with a space and concatenate, and you recover the original string byte for byte.

Special tokens

Every real tokenizer reserves ids that correspond to no text:

TokenPurposeNote
[CLS] / <s>Sequence-initial position whose final hidden state is used as a sentence representationBERT-style classification heads read this position
[SEP] / </s>Separates two segments, or marks the endSentence-pair tasks depend on it
[PAD]Fills short sequences so a batch is rectangularMust be excluded by the attention mask, or it contributes to the output
[MASK]The hidden position in masked language modellingPresent at pre-training, absent at fine-tuning — a known train/serve mismatch
[UNK]Fallback for unrepresentable inputAbsent from byte-level tokenizers

Special tokens are why you must use the tokenizer that shipped with a checkpoint. The ids are not portable: id 101 means [CLS] to one model and something else entirely to another. Loading a model with the wrong tokenizer does not raise an error; it silently produces nonsense.

Trap. Do not lowercase text before feeding a cased checkpoint, and do not strip accents before a tokenizer whose vocabulary contains accented pieces. The tokenizer object already contains the normalizer that the model was trained with. Adding your own normalization in front of it creates a mismatch between training and serving that shows up as a quiet accuracy loss, never as an exception.

13 · Vocabulary size, fertility, sequence length mathinteractive

With subwords, the OOV rate stops being the interesting number. A byte-level tokenizer has an OOV rate of exactly zero by construction, and a WordPiece tokenizer with a full character set has one near zero. Reporting "our OOV rate is 0.0%" says nothing about tokenizer quality — it restates a property of the algorithm.

The quantity that actually varies is fertility, the average number of pieces per word:

fertility = (number of pieces emitted) / (number of whitespace-delimited words)

Fertility is what the vocabulary size buys you. Bigger vocabulary, fewer pieces per word, shorter sequences, cheaper attention — and a bigger embedding matrix with rarer rows. The relationship has diminishing returns: doubling the vocabulary does not halve the fertility, because the pieces you add are by definition the less frequent ones.

What to measure instead of OOV

  1. Fertility on your domain, not on news text. A tokenizer trained on web English will fragment clinical notes, chemical names, and log lines. Compute pieces per word on a sample of your actual traffic.
  2. Total token count for a fixed corpus. This is the number that becomes latency and cost. Compare candidate tokenizers on the same 10,000 documents and report both totals.
  3. Continued-word rate. The share of words that emitted more than one piece. A single number, easy to explain, and it moves sharply when the domain shifts.
  4. Round-trip fidelity. Assert decode(encode(s)) == s over a sample that includes emoji, non-Latin scripts and control characters. A tokenizer that fails this is silently corrupting data.
  5. Per-language token cost. For a multilingual product, tokenize the same content in each supported language and compare. Large disparities mean some users get less context and pay more for it.
  6. Piece-count distribution, not the mean. A mean fertility of 1.3 hides the case where 2% of your documents fragment at 6 pieces per word. Look at the tail.

The short version of each

  • Contractions. Decide once, write it down: keep don't whole, expand it to do not, or split it into do + n't. All three are defensible; silently doing different things in training and serving is not.
  • Hashtags and mentions. The # and @ characters carry meaning. Keeping #NLProc whole creates a rare type; splitting the marker off loses the fact that it was a tag. A middle path is to keep the marker as its own token and let the subword tokenizer handle the rest, which also splits camel-case tags into readable pieces.
  • Emoji. They are ordinary code points and often the strongest sentiment signal in a short message. Some are single code points; others are sequences joined with zero-width joiners, and naive character-level slicing will cut them in half and produce mojibake. Use code-point-aware iteration.
  • URLs, emails, handles. Each one is a unique string that fragments into a dozen meaningless pieces. Detect them with a regex and replace with a placeholder before tokenizing, unless the URL itself is your signal.
  • Code. Underscores, dots and camel case are semantic. A tokenizer trained on prose will split user_id and groupby arbitrarily and will spend tokens on indentation. Code models use tokenizers trained on code, sometimes with whitespace-run pieces so that indentation costs one token rather than sixteen.
  • Non-English scripts. No spaces in Chinese and Japanese, so whitespace tokenization returns one enormous token. Rich morphology in Turkish and Finnish, so word-level vocabularies explode. Right-to-left and bidirectional text needs care at the display layer. This is the case SentencePiece and byte-level fallbacks exist for.
  • Mixed content. The genuinely hard input is a message with a hashtag, an emoji, a URL, a code snippet and two languages. Test on that, not on a clean paragraph.

15 · Why transformers tokenize this way math

Pulling the threads together. A transformer imposes four constraints, and subword tokenization is the design that satisfies all four at once.

  1. The output layer is a softmax over the entire vocabulary. Producing logits costs O(V · d) per position, at every position, at every step of generation. A vocabulary of a million word types is not affordable; tens of thousands is.
  2. The embedding matrix is V × d parameters. With d = 768 and V = 50,000 that is about 38 million parameters spent on the lookup table alone. Grow V to keep the tail and those extra rows are the ones seen least during training — you pay for parameters that are also the worst estimated.
  3. Attention is quadratic in sequence length. Every extra piece per word costs compute superlinearly and shrinks the effective context window. This rules out character level as a default.
  4. Language is open. New names, products, misspellings, identifiers and slang appear continuously; Heaps' law says the vocabulary never closes. A generative model that can emit [UNK] has a hole in its output space that cannot be filled at decoding time.

Subword tokenization threads all four: a fixed, modest symbol set (constraints 1 and 2), sequences only modestly longer than word level (constraint 3), and total coverage through character or byte fallback (constraint 4). It also delivers a benefit nobody designed for: morphological structure appears in the segmentation for free, so token, tokenize, tokenizer and tokenization share a piece and therefore share representation, without any linguistic resource being consulted.

Two properties worth stating explicitly because they are easy to lose:

  • Determinism. The same string must produce the same ids every time, on every machine. Any randomness — a hash-order dependency, an unstable tie-break — becomes a bug that appears only in production.
  • Reversibility. decode(encode(s)) should return s. Lossy normalization inside the tokenizer (accent stripping, aggressive case folding) breaks this, which is why modern tokenizers keep the normalizer explicit and configurable rather than hard-coded.
Connecting to the topic project. The TokenForge service asks you to expose both pipelines behind one API: classical preprocessing on one endpoint and at least two subword tokenizers on another, with every run persisted so configurations can be compared. Two design notes follow directly from these notes. First, the "Compare Tokenizers" view should report fertility and total piece count, not OOV rate — with byte-level BPE the OOV rate is zero and the comparison is empty. Second, the run record should store the full configuration (normalization form, case policy, stop list identity, tokenizer name and revision) alongside the counts, because a token count without its configuration is not reproducible and cannot be compared against anything.
