Topic 6 — Part-of-Speech Tagging as Token Classification

From a lookup table you can read with your own eyes to a fine-tuned transformer token classifier — and an honest account of when the transformer loses.

1 · POS tagging is token classification

A part-of-speech tagger takes a sequence of tokens and assigns one label to each token. That is the whole task. It is not sequence classification (one label for the whole input) and it is not generation (a new sequence of arbitrary length). It is token classification: the output has exactly the same length as the input, and position i of the output is a label for position i of the input.

tokens :  The   run   was   long   .
tags   :  DET   NOUN  AUX   ADJ    PUNCT

That one-to-one structure is what makes the whole topic tractable. It means:

  • Evaluation is trivial to define. Compare the predicted tag with the gold tag, token by token. Count matches. There is no alignment problem at the word level, no BLEU, no human judgement.
  • A dumb model is available. Because each token gets its own label, you can predict a token's label from the token alone, ignoring everything around it. That is the lookup baseline in section 5, and it is much better than it has any right to be.
  • The same head works for other tasks. Named-entity recognition, chunking, and error detection are all token classification. The Hugging Face class is AutoModelForTokenClassification for all of them; only the label set changes.

POS tags matter downstream because they are cheap syntax. A parser wants to know whether book is the head of a noun phrase or a verb; an information-extraction rule that looks for "adjective immediately before a product noun" needs the adjective label; a search index that stems only verbs needs to know which tokens are verbs. When the tagger is wrong, those consumers are wrong silently — nothing crashes, the output is just subtly worse.

2 · Tag sets: 17 universal tags, and 45 interactive

A tag set is the fixed, finite list of labels your tagger is allowed to output. Choosing it is a design decision that you make before you touch a model, and it determines what your confusion matrix looks like, what counts as an error, and whether your numbers are comparable to anyone else's.

The Universal Dependencies project defines 17 universal POS tags (UPOS). They are deliberately coarse and deliberately cross-lingual: the same 17 labels are used for every treebank in every language in the project, which is what makes cross-lingual comparison possible at all.

Widget 1 · The 17 universal tags, with frequency

Click a tag. The bar chart is an illustrative token-frequency profile for English newswire-style text — it has the right shape (a handful of tags carry most of the mass) but the exact percentages are synthetic, not measured.

The other tag set you will meet is the Penn Treebank set, usually quoted at 45 tags. It is finer: instead of one VERB tag it has six (VB VBD VBG VBN VBP VBZ), instead of one NOUN it has NN and NNS, instead of one ADJ it has JJ JJR JJS. That extra detail is genuinely useful if you need tense or number downstream.

It is also much harder to read. Three concrete reasons, and they are not aesthetic complaints:

  1. The matrix is 6.9× bigger. A 17-tag confusion matrix has 289 cells, 272 of them off-diagonal. A 45-tag matrix has 2,025 cells, 1,980 off-diagonal. At a readable cell size the 45-tag matrix does not fit on a screen; shrink it to fit and the labels collide. You can no longer find the big confusions by looking — you have to sort a list, at which point the picture is not doing any work.
  2. Errors get scattered. A single conceptual confusion ("the model muddles nouns and verbs") lands in one cell in UPOS and in twelve cells in PTB (2 noun tags × 6 verb tags). Each cell is individually small, so a real, systematic problem looks like noise.
  3. Some distinctions disappear, others appear. PTB's IN covers both prepositions and subordinating conjunctions, so the ADP/SCONJ confusion — one of the most common in UPOS — is literally invisible in a PTB matrix. Meanwhile a large share of the PTB matrix's off-diagonal mass sits inside a coarse class (VBD vs VBN, NN vs NNS), which is a different, usually less interesting kind of error.

For this course, use UPOS. You get a matrix you can actually stare at, and Universal Dependencies gives you the treebanks with those tags already in them. You will see both matrices side by side in section 13.

3 · Lexical ambiguity mathinteractive

Here is the fact that makes POS tagging a real task rather than a dictionary lookup: the same word takes different tags in different contexts. The word type is fixed; the tag is not.

WordSentenceTagWhat decides it
bookI read the book on the table .NOUN A determiner before it makes it a noun; an imperative frame makes it a verb.
Please book a table for two .VERB
runThey run a small shop .VERB Subject pronoun before it → verb; determiner before it → noun.
The run was long .NOUN
thatShe said that they run .SCONJ Three different jobs for one spelling. This is the single most confusing English function word.
I like that book .DET
The book that I read was long .PRON
likeI like the book .VERB Verb, preposition, and subordinating conjunction all share the spelling.
It looks like rain .ADP
Like I said , it was long .SCONJ

Now quantify it. If a tagger is context-free — if it sees only the word type and nothing else — then for a given word type w the best it can possibly do is always emit the tag that w takes most often. Its accuracy on that word is capped:

ceiling(w) = maxt count(w, t) / Σt count(w, t)

This is not a property of any particular algorithm. It is an upper bound that no context-free method can beat, because a context-free method must return the same answer every time it sees w. If that is SCONJ 49% of the time, DET 29%, and PRON 22%, then any context-free tagger gets at most 49% of the that tokens right, and there is nothing to tune.

Widget 2 · Ambiguity explorer — the same word, two tags, one answer

Pick a word. The lookup emits one tag for every occurrence; each example is marked right or wrong against its gold tag. Counts are illustrative but the ceiling arithmetic is computed from them.

The trap. Ambiguity is concentrated in a small number of very frequent word types. Most word types in a corpus are unambiguous; most ambiguous types are common function words, so a large share of ambiguous tokens comes from a handful of spellings. That is why the lookup baseline scores so high — and why every point above it has to be won on exactly those few words.

4 · Counting: building the lookup table interactive

The baseline you will build has no training loop, no gradients, and no hyperparameters. It has one pass over a tagged corpus and a dictionary.

counts = {}                       # word -> {tag: n}
for sentence in train:
    for word, tag in sentence:
        w = word.lower()
        counts.setdefault(w, {})
        counts[w][tag] = counts[w].get(tag, 0) + 1

lookup = {w: max(d, key=lambda t: (d[t], t is not None and -ord(t[0]))) for w, d in counts.items()}

That last line is doing something subtle, so write it plainly instead. Ties happen constantly on small corpora, and a tie broken by dictionary insertion order is a silent source of irreproducible results. Break ties deterministically:

def most_frequent_tag(d):
    # sort by count descending, then tag name ascending -> fully deterministic
    return sorted(d.items(), key=lambda kv: (-kv[1], kv[0]))[0][0]

lookup = {w: most_frequent_tag(d) for w, d in counts.items()}

Here is the five-sentence corpus we will use for the rest of these notes. It is tiny on purpose: you can verify every number in it yourself.

S1  I/PRON read/VERB the/DET book/NOUN on/ADP the/DET table/NOUN ./PUNCT
S2  Please/INTJ book/VERB a/DET table/NOUN for/ADP two/NUM ./PUNCT
S3  They/PRON run/VERB a/DET small/ADJ shop/NOUN and/CCONJ they/PRON run/VERB it/PRON well/ADV ./PUNCT
S4  The/DET run/NOUN was/AUX long/ADJ ./PUNCT

5 · The most-frequent-tag baseline math

The baseline is now one line of inference:

taĝ(w) = argmaxt count(w, t)   if w ∈ lookup,   else fallback(w)

Four properties, and each of them is a reason to build it before you build anything else:

PropertyWhy it matters
No training. One counting pass, seconds on a full treebank. You have a number to beat on day one, before the GPU queue clears.
Completely inspectable. The model is a dictionary. You can print it, diff two versions, and read the entry for any word. Every prediction has a one-line explanation: "the training corpus tagged run as VERB 2 times and NOUN 1 time." No attribution method, no attention map, no hand-waving.
Deterministic. Same corpus, same table, same predictions, forever. Any change in your numbers is a change in your data or your evaluation code, never in a random seed.
Already around 90% on English. This is the standard textbook result for the most-frequent-tag baseline on English treebank data. It sets the bar where it belongs. A transformer at 91% is not "working" — it is barely earning its keep.

That last row is the one students find hardest to believe, so take it apart. The baseline gets roughly nine tokens in ten right without looking at context at all, because:

  • A large share of tokens are punctuation, determiners, prepositions, pronouns, and auxiliaries — high-frequency closed-class words that are nearly always the same tag.
  • Content words are individually rarer but overwhelmingly unambiguous: table, shop, treebank, corpus take one tag essentially always.
  • The ambiguous words are frequent, but for most of them one tag dominates heavily, so "always guess the dominant tag" is right most of the time even on them.
Read the baseline number the right way. "The transformer got 96.5%" means nothing on its own. "The transformer got 96.5% where the lookup got 90.2%, so it removed 64% of the baseline's errors" is a claim you can defend. Always report the error reduction, not just the accuracy: (acc_model − acc_base) / (1 − acc_base).

7 · Unknown words and the fallback rules interactive

Every word type your tagger has never seen is a hole in the dictionary. On a real treebank, somewhere between 2% and 8% of test tokens are unknown depending on the domain gap, and nearly all of the baseline's remaining error lives in those tokens. That is the single most important operational fact about this baseline: the known words are almost solved, the unknown words are almost a coin flip, and the overall number is a weighted average of the two.

You cannot look them up, so you look at their shape. The classic fallback is an ordered list of rules on the surface form:

def fallback(token, is_first_word):
    if all(not c.isalnum() for c in token):        return "PUNCT"
    if any(c.isdigit() for c in token):            return "NUM"
    if token[0].isupper() and not is_first_word:   return "PROPN"
    if token.endswith("ly"):                       return "ADV"
    if token.endswith(("ing", "ed")):              return "VERB"
    if token.endswith("est"):                      return "ADJ"
    if token.endswith(("ous", "ive", "al", "ful")):return "ADJ"
    if token.endswith(("tion","ment","ness","ity")):return "NOUN"
    if token.endswith("s"):                        return "NOUN"
    return "NOUN"                                  # default: unknown words are usually nouns

Order matters and is part of the model. dangerous ends in both -ous and -s; the ADJ rule has to come first or you get NOUN. kindness ends in both -ness and -s; same story.

The default of NOUN is not arbitrary. New word types entering a language are overwhelmingly nouns — product names, jargon, borrowings, typos of nouns — so guessing NOUN when nothing else fires is the right prior.

Widget 5 · Suffix-rule editor — turn rules off and watch accuracy move

36 held-out "unknown" words with gold tags. Toggle a rule and the tagger re-runs. The right-hand column shows what happens to accuracy if you turn that rule off from the current configuration — computed live, not hard-coded.

Three findings you should be able to reproduce in that widget, because they generalise:

  1. Two rules are redundant. With a NOUN default, the -tion/-ment/-ness/-ity → NOUN rule and the -s → NOUN rule change nothing at all on this set: every word they fire on would have fallen through to NOUN anyway. Deleting them costs zero accuracy and removes two things to maintain. Rules that agree with your default are decoration.
  2. Turning a rule off can help. The -est → ADJ rule wins on largest, smallest, brightest and loses on interest and forest, so its net value on this set is small. The -ly → ADV rule is worth more, but it still costs you family and reply. A suffix rule is a bet, not a fact.
  3. The default carries most of the weight. All rules off, guessing NOUN every time, is already about 42% on this set. That is the number your rules have to beat, and each individual rule buys only a few points.
Do not silently drop unknown words from evaluation. If your evaluation loop skips tokens the lookup has no entry for, you have deleted the only hard part of the task and your baseline number is fiction. Report accuracy on all tokens, and separately on known and unknown tokens. The split is the interesting result.

55.6% is far below the ~90% figure from section 5, and the reason is entirely the corpus size. With 37 training tokens, 4 of 9 test tokens are unknown (44%); on a real treebank that figure is a few percent. Scale the corpus and the known-token share goes up, the known-token accuracy goes up (because counts become reliable), and the overall number climbs toward 90%.

Now read the errors, which is the actual point of the exercise:

  • book and run are ambiguity errors. The lookup could not have got both right. It says NOUN for book and VERB for run, and this sentence needs the opposite of each. Notice that this is not a bug and not fixable by more data — more data makes the table more confident in exactly the wrong answer for these two tokens. You need context to fix them, and that is the whole argument for the transformer.
  • morning is a rule error. The -ing → VERB rule fires on a noun. Fixable in principle — add morning to the lexicon, or drop the rule — but every patch you add is a new bet that can lose elsewhere.
  • in is a coverage error. A preposition fell through to the NOUN default because 37 tokens were not enough to have seen it. This class of error vanishes with corpus size: closed-class function words are essentially never unknown on a real training set. Do not over-learn from it.
Do this by hand once. Building the table, tagging a sentence, and classifying each error into ambiguity / rule / coverage takes fifteen minutes and permanently changes how you read a confusion matrix. Every number you will produce later in this topic is this computation at scale.

9 · Why this baseline is the right comparison

You could compare your transformer to a random tagger, to a majority-class tagger (everything is NOUN, roughly 17%), or to a published number from someone else's paper. All three are worse choices. Here is the case for the lookup.

It is the strongest thing that is still explainable

A baseline has one job: to tell you how much of your model's score is coming from the task and how much from your model. The lookup captures everything that is learnable from the word identity alone — which, in POS tagging, is most of it. Whatever the transformer adds on top is, by construction, the contribution of context. That is exactly the quantity your report is about.

When it is wrong, you can point at the word

This is the property that makes it worth building rather than citing. Take any error the lookup made and you get a complete, checkable explanation in one line:

token 6: "run"
  lookup entry: {VERB: 2, NOUN: 1}  ->  predicts VERB
  gold: NOUN
  diagnosis: lexical ambiguity. A context-free tagger cannot resolve this.
             Ceiling for "run" is 2/3 = 66.7%; this token is in the losing third.

You can put that in a report. You can show it to someone who has never seen a neural network and they will understand both the error and why context is required to fix it. Compare with the corresponding statement about a transformer error — "the model assigned probability 0.61 to VERB" — which explains nothing.

Concretely, the lookup partitions its own errors into three buckets you can count exactly: ambiguity errors (the word is in the table, gold tag is not the most frequent one — irreducible without context), rule errors (unknown word, a suffix rule fired and was wrong), and coverage errors (unknown word, nothing fired, took the default). Compute those three numbers for your baseline and you have a map of where a better model could possibly help. If 80% of the baseline's errors are ambiguity errors and your transformer only improves by 2 points, your transformer is not using context.

It is honest about the domain

Run the lookup built on treebank A over test data from domain B and the unknown-word rate tells you the domain gap in a single number, before you train anything. That is a cheap and unusually trustworthy diagnostic.

Historical aside — HMMs. Before neural taggers, the standard statistical approach was a hidden Markov model: emission probabilities P(word | tag), transition probabilities P(tagi | tagi−1), and Viterbi decoding to find the best tag sequence. It works, it uses context (a one-tag window), and it was state of the art for years. It is worth knowing that it exists and that it is where "tagging is a sequence problem" comes from. It is not the baseline in this course: it needs training, its parameters are not directly readable, and its errors do not reduce to a one-line explanation. The lookup is the baseline. If you want a middle rung on the ladder, add a second lookup keyed on (previous tag, word) rather than reaching for an HMM.

10 · Fine-tuning a transformer token classifier code

The transformer side is standard and short. An encoder produces one contextual vector per subword; a linear head maps each vector to 17 logits; cross-entropy is summed over positions. The only interesting part is the data preparation, which is section 11.

from transformers import AutoTokenizer, AutoModelForTokenClassification

LABELS = ["ADJ","ADP","ADV","AUX","CCONJ","DET","INTJ","NOUN","NUM",
          "PART","PRON","PROPN","PUNCT","SCONJ","SYM","VERB","X"]      # 17 UPOS tags
id2label = {i: l for i, l in enumerate(LABELS)}
label2id = {l: i for i, l in enumerate(LABELS)}

tok = AutoTokenizer.from_pretrained("distilbert-base-cased")
model = AutoModelForTokenClassification.from_pretrained(
    "distilbert-base-cased",
    num_labels=len(LABELS), id2label=id2label, label2id=label2id)

Three choices in that block that are not free:

  • A cased checkpoint. Capitalisation is one of the strongest signals for PROPN. An uncased model throws it away before the encoder sees it, and your PROPN recall drops for a reason that will take you an afternoon to find.
  • Pass id2label and label2id. Otherwise the saved model reports LABEL_0 … LABEL_16 and anyone loading it — including you, in three weeks — has to guess the order. This is free correctness; take it.
  • num_labels must match your tag set exactly. If your treebank uses 17 UPOS tags but you pass 18 "just in case", you get a dead logit that macro-F1 will happily count as a tag with F1 = 0 and drag your score down.

Loading the data: get an English treebank from universaldependencies.org. The CoNLL-U format is one token per line, tab-separated, with the UPOS tag in column 4 and blank lines between sentences. A reader is about fifteen lines:

def read_conllu(path):
    sents, toks, tags = [], [], []
    for line in open(path, encoding="utf-8"):
        line = line.rstrip("\n")
        if not line:
            if toks: sents.append((toks, tags)); toks, tags = [], []
            continue
        if line.startswith("#"): continue
        f = line.split("\t")
        if "-" in f[0] or "." in f[0]: continue     # skip multiword and empty nodes
        toks.append(f[1]); tags.append(f[3])        # FORM, UPOS
    if toks: sents.append((toks, tags))
    return sents

Skipping the multiword-token ranges (lines with IDs like 7-8) and empty nodes (IDs like 5.1) is not optional — include them and your token counts will not match your tag counts, and the mismatch will surface as an off-by-one alignment error three steps later.

Training arguments worth stating explicitly, with reasons rather than magic numbers: a small learning rate (fine-tuning, not training from scratch), two to four epochs (POS tagging converges fast because the task is easy and the signal is dense — every token is a training example), and evaluation every epoch on the dev split so you can see over-fitting when it starts. Then:

import numpy as np
from sklearn.metrics import accuracy_score, f1_score, confusion_matrix

def compute_metrics(eval_pred):
    logits, labels = eval_pred
    preds = np.argmax(logits, axis=-1)
    mask = labels != -100                       # drop specials + continuation subwords
    y_true = labels[mask]
    y_pred = preds[mask]
    return {
        "accuracy": accuracy_score(y_true, y_pred),
        "macro_f1": f1_score(y_true, y_pred, average="macro", zero_division=0),
    }

The Hugging Face course section on token classification (huggingface.co/learn/nlp-course/chapter7/2) walks through the same pipeline for NER; the only difference for POS tagging is the label set and the fact that you do not need BIO decoding, because POS tags are not spans.

11 · The subword alignment problem interactive

Here is the trap that costs more marks than anything else in this topic. Your gold data has one tag per word. Your tokenizer produces one embedding per subword, and a word can become one, two, or five subwords. The lengths do not match, and if you line them up wrong nothing crashes — you get a model that trains happily, reports a plausible loss curve, and is quietly garbage.

words    : The  tokenizer        splits      unbelievable            words  into  subwords     .
subwords : The  token ##izer     split ##s   un ##bel ##iev ##able   words  into  sub ##words  .
             8 words  ->  14 subwords

The convention: assign the word's tag to the first subword of that word, and assign -100 to every continuation subword and to the special tokens. PyTorch's cross-entropy ignores -100 by default, so those positions contribute nothing to the loss. At prediction time you read the tag off the first subword of each word.

def align(words, tags, tokenizer):
    enc = tokenizer(words, is_split_into_words=True, truncation=True)
    word_ids = enc.word_ids()          # e.g. [None, 0, 1, 1, 2, 2, 3, 3, 3, 3, ..., None]
    labels, prev = [], None
    for wid in word_ids:
        if wid is None:                # [CLS] / [SEP] / padding
            labels.append(-100)
        elif wid != prev:              # FIRST subword of a new word -> real label
            labels.append(label2id[tags[wid]])
        else:                          # continuation subword -> ignored
            labels.append(-100)
        prev = wid
    enc["labels"] = labels
    return enc

word_ids() is the whole solution. It is provided by the fast tokenizers and it tells you, for every subword position, which original word it came from. If you find yourself writing zip(subwords, tags), stop: that is the bug.

Widget 6 · Subword alignment — correct, label-all, and the off-by-one bug

Each strip shows the 14 subwords with the label assigned to each position. Read-back is done the way inference does it: take the predicted tag at the first subword of each word. Accuracy is computed from that read-back, assuming the model learns whatever labels you gave it.

What the four strategies actually do:

StrategyEffect
First subword onlyCorrect. Loss is computed once per word, so every word contributes equally regardless of how many subwords it splits into.
Label every subwordTrains and gets the read-back right, but re-weights the loss: unbelievable contributes four times as much as words. It also inflates any accuracy you compute at the subword level, because continuation subwords are easy. If you report subword-level accuracy you are not reporting POS tagging accuracy.
zip(subwords, tags)Catastrophic and silent. Tags slide leftward from the first multi-subword word onward; every word after it is trained on somebody else's label, and the tail of every sentence gets no label at all. Loss still decreases — the model learns the wrong function competently.
Last subword onlyRead-back matches if you also read from the last subword. Mixing the two — train on last, predict from first — is another silent failure. Pick one convention and use it in both places.
How to catch it in thirty seconds. After building your dataset, take one example, zip the subword strings with the label ids, and print the pairs where the label is not −100. Every printed pair must be (first subword of a word, that word's tag). Do this before you launch training, every single time. If the printout looks right, the alignment is right; if you skip the printout, you will find out from a confusion matrix a day later.

12 · Token accuracy versus macro-F1 mathinteractive

Two numbers, and they answer different questions.

Token accuracy is the fraction of tokens tagged correctly. It weights every token equally, which means it weights every tag by how often that tag occurs. NOUN, PUNCT, VERB, ADP and DET together are the bulk of the tokens, so accuracy is mostly a report on those five.

accuracy = (Σt M[t][t]) / (Σt Σp M[t][p])

Macro-F1 computes precision, recall and F1 per tag and then takes an unweighted mean over tags. Every tag counts once, whether it has 1,700 tokens or 10.

Pt = M[t][t] / Σg M[g][t]    Rt = M[t][t] / Σp M[t][p]    F1t = 2 Pt Rt / (Pt + Rt)
macro-F1 = (1/T) Σt F1t

The consequence: rare tags dominate macro-F1. With 17 tags, a single tag going from F1 = 1.0 to F1 = 0.0 costs you 1/17 ≈ 5.9 macro-F1 points no matter how rare it is. If that tag has 10 tokens out of 10,000, it costs accuracy 0.1 points. Three rare tags collapsing costs 17.6 macro-F1 points and 0.3 accuracy points. The two metrics will tell you completely different stories about the same model, and both stories are true.

Practical guidance:

  • Report both, always. Accuracy alone hides a model that has given up on the tail. Macro-F1 alone makes a model that is excellent at the tags anyone cares about look mediocre.
  • Report the support column. A macro-F1 built on a tag with 4 test tokens is not measuring anything stable — one token flips it by 25 recall points. Print per-tag support next to per-tag F1 so the reader can discount the noisy rows.
  • Use zero_division=0 and know what it does. If your model never predicts SYM, precision for SYM is 0/0. Setting it to 0 is the conservative choice and it will visibly hurt macro-F1 — which is the correct outcome, because a tag you never predict is a tag you have failed at.
  • Do not compare macro-F1 across different tag sets. Macro-F1 over 17 tags and macro-F1 over 45 tags are simply different quantities — a different number of terms in the average, over a different set of distinctions. The 45-tag figure is usually lower for the same model because it averages over more rare tags, but the direction is not guaranteed, so the comparison is meaningless either way. State the tag set every time you state a macro-F1.

13 · Confusion matrices over tags interactive

A confusion matrix M over tags has gold tags on rows and predicted tags on columns: M[g][p] is the number of tokens whose gold tag is g and whose predicted tag is p. The diagonal is correct predictions. Everything else is an error with a name.

Read it in this order:

  1. Find the largest off-diagonal cells. These are your systematic errors. Two or three of them usually account for most of the total error mass.
  2. Check whether they are symmetric. If NOUN→VERB and VERB→NOUN are both large, the model has not learned the distinction. If only ADJ→NOUN is large, the model has a bias: it over-predicts NOUN, probably because NOUN is the majority class.
  3. Look along each rare row. A rare tag with a near-empty diagonal and all its mass in one column is a tag the model has effectively deleted from its output space.
  4. Pull three real sentences per large cell. A confusion matrix tells you what; only the sentences tell you why. This is what the deliverable asks for when it says "identify ambiguous word classes where the models disagree and give a worked example of each".

The confusions that show up on English POS tagging, and what causes each:

ConfusionTypical causeExample
NOUN ↔ VERBZero-derivation: English lets almost any noun be a verb and vice versa, with no morphological marking.the run was long vs they run a shop
NOUN ↔ PROPNCapitalisation is the main cue and it is unreliable: sentence-initial words, headlines, all-caps text.Apple fell — fruit or company
ADJ ↔ NOUNNoun-noun compounds. The modifier looks like an adjective slot but is tagged NOUN.the treebank corpus
ADJ ↔ ADVFlat adverbs with no -ly.drive fast (ADV) vs a fast car (ADJ)
ADP ↔ SCONJThe same word introduces a noun phrase or a clause.before dinner (ADP) vs before we ate (SCONJ)
AUX ↔ VERBhave, be, do are auxiliaries in some frames and main verbs in others.I have eaten (AUX) vs I have a book (VERB)
DET ↔ PRONDeterminer or standalone pronoun, same spelling.that book (DET) vs I saw that (PRON)
PART ↔ ADPto before an infinitive versus to as a preposition.to run (PART) vs to the shop (ADP)

Every row of that table is a place where the transformer should beat the lookup, because every one of them is resolvable from the neighbouring words. If your transformer does not improve on these cells, it is not using context and something is wrong with your setup — most likely the alignment from section 11.

14 · When the transformer loses to the lookup

It happens, it is not rare, and pretending otherwise is the fastest way to fail an evaluation. A transformer token classifier that has been fine-tuned badly can and does score below a dictionary you built in four seconds. Here is the list of causes, roughly in order of how often they are the actual explanation:

CauseSymptom in the numbersFix
Broken subword alignment Accuracy plateaus far below baseline; loss still decreases smoothly; the confusion matrix looks scrambled rather than structured — errors are spread everywhere instead of concentrated on the pairs in section 13. Print the (subword, label) pairs. Use word_ids().
Train/eval convention mismatch Train loss is fine, dev accuracy is bizarre. Often you trained on first-subword labels and evaluated on every subword, or forgot to mask -100 in compute_metrics. Mask labels != -100 in the metric, and read back from the same subword you trained.
Too little training Accuracy climbing steadily when you stopped. One epoch on a small treebank is not enough for 17-way classification to settle. Train to convergence on dev; POS tagging is cheap.
Learning rate too high Loss spikes then flattens at a high value; the model collapses to predicting NOUN (or the majority tag) everywhere. Accuracy ≈ the NOUN share; macro-F1 near zero. Lower it by an order of magnitude and use warmup.
Uncased checkpoint Overall accuracy close to baseline, but PROPN recall much worse than the baseline's. The lookup's capitalisation rule beats a model that cannot see capitalisation. Use a cased checkpoint.
Label-id scrambling Accuracy near chance, confusion matrix is a permutation of a good one — high mass in a scattered set of off-diagonal cells, low on the diagonal. Build label2id once, from a sorted list, and use it for both encoding and decoding.
Truncation Accuracy fine on short sentences, poor on long ones. Tokens past max_length were silently dropped, and if you padded the label list to match, the tail is misaligned too. Check the length distribution; raise max_length or use striding.
Domain gap Both models drop, but the transformer drops further. It over-fit surface patterns of the training domain; the lookup at least still knows the closed-class words. Report it as a finding. This is a real result, not a bug.

The honest finding is worth stating in your report if you get it: "our fine-tuned transformer scored 88.1% token accuracy against the lookup baseline's 90.4%. Investigation showed X." A negative result that you diagnosed is worth more than a positive result you cannot explain. What is not acceptable is reporting the transformer number without the baseline number, or quietly dropping the baseline when it wins.

The diagnostic that finds it fastest. Compute the two confusion matrices and subtract them: Mtransformer − Mlookup. Cells where the transformer is worse show up as positive off-diagonal entries. If those cells are the ambiguity pairs from section 13, your model is under-trained. If they are scattered with no linguistic pattern, your data pipeline is broken — go back to section 11.

15 · What to report, and where to read more

For the topic project (TagWise), the evaluation section should contain all of the following. None of it is optional and all of it follows from the sections above.

  1. The tag set and the data. Which treebank, which splits, how many sentences and tokens in each, and the tag distribution. Include the number of tag types actually present — if the treebank never uses X, say so, because it changes macro-F1.
  2. The baseline, fully specified. Lowercasing policy, tie-breaking rule, the ordered list of fallback rules, and the default tag. Someone should be able to rebuild your exact table from the description.
  3. Unknown-word rate on the test split, plus accuracy split three ways: overall, known tokens, unknown tokens. For both models.
  4. Token accuracy and macro-F1 for both models, with a per-tag table showing precision, recall, F1 and support.
  5. Error reduction of the transformer over the baseline, not just the raw accuracies.
  6. A confusion matrix over the 17 tags for each model, and the top five off-diagonal cells listed numerically underneath — because nobody can read the top five off a heat map reliably.
  7. At least three ambiguous word classes where the two models disagree, each with one worked example: the sentence, the gold tag, both predictions, and one sentence of diagnosis. Section 8 shows the format.
  8. The honest comparison. If the baseline won on some measure, say which and why.
