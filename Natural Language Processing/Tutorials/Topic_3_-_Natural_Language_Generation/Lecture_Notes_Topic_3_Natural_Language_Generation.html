Topic 3 — Controllable Natural Language Generation with a Decoder Transformer

How a decoder-only model turns a prompt into text one token at a time, what every decoding knob actually does to the probability distribution, and how to tell whether the output is any good.

What you should walk away with. (1) You can explain autoregressive generation and why the causal mask is what makes it possible. (2) You can turn a logit vector into probabilities by hand, and predict what temperature, top-k, and top-p will do to that vector before you run the code. (3) You can say precisely why greedy decoding produces flat, looping text and why beam search produces safe, interchangeable text. (4) You can compute perplexity from a list of token probabilities and state what it does not tell you. (5) You can design a human-rating protocol where disagreement between raters is information you keep, not noise you average away. (6) You can name four generation failure modes on sight and match each to a decoding fix.

1 · The decoder stack and the causal mask mathinteractive

A decoder-only transformer (the GPT family) is a stack of identical blocks. Each block does causal self-attention followed by a position-wise MLP, both wrapped in residual connections. The only structural difference from an encoder block is one line in the attention computation: before the softmax, every score that would let a position look at a later position is set to negative infinity.

scores = Q @ K.T / sqrt(d_k)          # (T, T)
scores = scores + causal_mask         # 0 on and below the diagonal, -inf above
attn   = softmax(scores, dim=-1)      # rows sum to 1; future columns get exactly 0
out    = attn @ V

Why -inf and not, say, zero? Because the mask is applied before the softmax. exp(-inf) = 0, so the masked entries contribute nothing to the row's normalizing sum and the surviving entries renormalize among themselves. If you instead zeroed the attention weights after the softmax, the rows would no longer sum to 1 and the output would silently shrink toward zero at early positions.

The mask has one consequence that governs everything else in these notes: the hidden state at position t is a function of tokens 0 … t only. That means a single forward pass over a sequence of length T produces T next-token predictions at once — position 0 predicting token 1, position 1 predicting token 2, and so on — and none of them cheated by looking ahead. This is why decoder-only models can be trained on raw text with no labels: every position is simultaneously an input and a target.

Training and generation are the same computation, run differently. During training you feed the whole true sequence in one pass and score all T predictions in parallel (teacher forcing). During generation you have no true sequence, so you feed what you have, take the prediction at the last position, append it, and feed the result back. Same weights, same mask, same math — only the loop is different.

Two practical notes. First, the mask is fixed and data-independent, so it is built once and reused. Second, because position t's keys and values never change when you append token t+1, they can be cached: this is the KV cache, and it is the difference between generation costing O(T²) and O(T³) in total. Nothing in these notes depends on the cache, but every real serving stack uses it.

2 · From hidden state to a next-token distribution mathinteractive

The last block emits a hidden vector h_t of size d_model for each position. A single linear layer — the language-modelling head, usually tied to the input embedding matrix — projects it to one score per vocabulary entry:

z = ht WLM⊤   ∈  ℝV

Those V numbers are the logits. They are unnormalized, unbounded, and can be negative. On their own they mean nothing absolute; only their differences matter. Softmax turns them into a probability distribution:

pi = exp(zi) / Σj exp(zj)

Three properties you should internalize, because every decoding strategy exploits one of them:

  • Shift invariance. Adding a constant c to every logit leaves p unchanged, since exp(z_i + c) cancels top and bottom. This is why implementations subtract max(z) before exponentiating: it prevents overflow and changes nothing.
  • Differences, exponentiated. The ratio p_i / p_j = exp(z_i - z_j). A logit gap of 1 means a probability ratio of e ≈ 2.72; a gap of 5 means a ratio of about 148. Small-looking logit gaps are large probability gaps.
  • Scaling is not shifting. Multiplying all logits by a constant does change p — it stretches or compresses those gaps. That single fact is all that temperature is (§7).

Practical consequence: a real vocabulary has roughly 30,000–100,000 entries, so the distribution at any step has a very long tail. Even after a confident prediction takes 50 % of the mass, the remaining 50 % is spread across tens of thousands of tokens, most of which would be nonsense in context. The tail is where sampling goes wrong, and truncation (§8, §9) exists to cut it off.

3 · Autoregressive generation, one token at a time mathinteractive



Generation factorizes the probability of a whole sequence into a product of conditionals — this is just the chain rule of probability, with the causal mask guaranteeing the model respects it:



P(w1 … wn) = ∏t=1n P(wt | w<t)



The loop is short enough to write out completely:



tokens = tokenizer.encode(prompt)
for step in range(max_new_tokens):
    logits = model(tokens).logits[-1]        # scores for the NEXT token only
    logits = apply_repetition_penalty(logits, tokens)
    logits = logits / temperature
    logits = truncate_top_k_top_p(logits, k, p)
    probs  = softmax(logits)
    next_id = choose(probs)                  # argmax, or a sample
    if next_id == eos_id: break
    tokens.append(next_id)



Everything this topic is about lives in the four lines between the forward pass and choose. The model weights are fixed; those four lines are what a user of your GenText service is actually adjusting when they move a slider.



Note the order, because it matters and is easy to get wrong. Repetition penalty acts on raw logits. Temperature divides logits. Truncation happens on the temperature-scaled distribution, so raising temperature widens the nucleus that top-p keeps. Finally the surviving mass is renormalized to sum to 1. Change the order and you change the output distribution — for example, applying top-p before temperature would let temperature reintroduce relative weight that top-p was supposed to have already fixed.




  Trap. The model is not "choosing" anything. It emits a distribution; your decoding code chooses. Two runs with identical weights and identical prompts can produce wildly different text purely because of the sampler. When a stakeholder says "the model said X", the honest answer is "the model assigned X some probability and our sampler drew it".

4 · Greedy decoding and the loop it falls into interactive



Greedy decoding takes the argmax at every step:



wt = argmaxi P(i | w<t)



It is deterministic, it is the cheapest possible decoder, and it is the right default for tasks where there is essentially one correct output — extracting a date, classifying with a generative model, emitting a JSON field. For open-ended text it fails in a specific and predictable way.



The failure is structural, not a bug in any particular model. Greedy decoding is a deterministic function from state to next token. In an n-gram-like conditioning window, the state is effectively the recent context. If the argmax path ever returns to a context it has already visited, it will make the same choice again, and the sequence enters a cycle from which it can never escape. The only thing that stops it is the length cap.



Watch it happen on the toy model from §3. Its greedy path is:



<bos> -> the -> coffee -> is -> rich -> and -> smooth -> and -> smooth -> and -> smooth -> ...



The cycle is and → smooth → and. Look at the two distributions that create it:



P(. | and)     -> smooth 0.309  rich 0.253  bitter 0.207  very 0.139  a 0.093
P(. | smooth)  -> and    0.441  .    0.361  but    0.198



Neither distribution is degenerate. After "and", the top choice holds only 31 % of the mass; after "smooth", ending the sentence is a perfectly respectable 36 %. Greedy throws away all of that. It takes 0.441 over 0.361 — a gap of eight percentage points — and by doing so it commits to never ending the sentence.



The same phenomenon in a real model is worse, because real models have a well-documented tendency for the probability of a repeated span to increase each time it repeats: the context now contains evidence that this text is the kind of text that repeats. The loop is self-reinforcing.

5 · Beam search: better likelihood, worse writing mathinteractive



Greedy is myopic: a token that looks best now may lead into a region of low-probability continuations. Beam search fixes the myopia by keeping the B highest-scoring partial sequences at every step, expanding all of them, and re-pruning to B. The score is a sum of log-probabilities, because probabilities of long sequences underflow:



score(w1 … wt) = Σi=1t log P(wi | w<i)



Because every term is negative, longer sequences score worse simply for being longer. Implementations therefore divide by tα for some length penalty α (often 0.6–1.0). Without it, beam search has a strong bias toward emitting the end-of-sequence token early — a real cause of the "abrupt truncation" failure mode in §15.



Beam search reliably finds sequences with higher total log-probability than greedy. That is exactly the problem. The highest-probability sequence under a language model trained on human text is not the most human-like sequence. Human text is surprising in a fairly consistent way; the mode of the distribution is bland. Push the beam width up and the surviving hypotheses converge on the same safe prefix, differing only in the last token or two. That is diversity collapse: you get B outputs that are variations on one sentence, not B alternatives.

  When to use beam search anyway. Constrained generation with a single acceptable answer: translation, grammatical error correction, structured summarization, code completion against a spec. Anything where you would be happy for two different users to get identical output. For a creative or conversational product, beam search is the wrong tool and no amount of tuning fixes it.





6 · Pure sampling: the opposite failure math



Pure (ancestral) sampling draws the next token from the full distribution, in proportion to its probability:



wt ∼ P(· | w<t)



This is the only strategy that is statistically true to the model. If you sampled infinitely many sequences this way, their frequencies would match the model's own beliefs exactly. Greedy, beam, top-k and top-p all sample from a distorted distribution on purpose.



So why is pure sampling almost never used for a product? Because of the tail. Suppose a step has 50,000 candidate tokens and the top 40 hold 95 % of the mass. The remaining 5 % is spread across 49,960 tokens, and essentially all of them are contextually wrong: a token from a different language, a rare proper noun, a stray punctuation mark. Each individual bad token has probability around 0.000001, which sounds negligible. But you get one draw per step, and the aggregate tail probability is 5 %.



Do the arithmetic. If the tail carries 5 % of the mass at every step, the probability of surviving a 200-token generation without a single tail draw is



(1 − 0.05)200 = 0.95200 ≈ 0.000035



Roughly one generation in 28,000 stays clean. And a single tail token is not a local blemish: it enters the context, and every subsequent token is conditioned on a prefix that now contains something incoherent. The model does its best to continue a broken sentence, and the output degrades from there. This compounding is the whole argument for truncation. You are not trying to remove unlikely tokens because they are unlikely; you are removing them because one draw from the tail poisons everything downstream.

7 · Temperature as a reshaping of the distribution mathinteractive



Temperature divides the logits before the softmax:



pi(T) = exp(zi / T) / Σj exp(zj / T)



Recall from §2 that only logit differences matter. Dividing by T multiplies every difference by 1/T. So temperature is a single global control on how far apart the candidates are:



    
  
  • T < 1 sharpens. Gaps widen, the leader takes more mass, the tail shrinks toward zero.
    • 
  
  • T = 1 is the model's own distribution. No distortion.
    • 
  
  • T > 1 flattens. Gaps compress, the tail rises, unlikely tokens become reachable.
    • 




The two limits are worth knowing exactly, because they connect temperature to the other strategies:



    
  
  • T → 0+. The ratio p_i/p_j = exp((z_i - z_j)/T) blows up for any positive gap, so all mass concentrates on the argmax. Temperature zero is exactly greedy decoding. (Libraries usually special-case T = 0 to argmax rather than dividing by zero.)
    • 
  
  • T → ∞. Every z_i/T → 0, so every exp term goes to 1 and p_i → 1/V. Infinite temperature is uniform random token choice — the model contributes nothing.
    • 




Worked example. Take three logits z = [2.0, 1.0, 0.0].



T = 1.0 :  exp(2.0)=7.389  exp(1.0)=2.718  exp(0.0)=1.000   sum=11.107
           p = [0.665, 0.245, 0.090]

T = 0.5 :  z/T = [4, 2, 0]
           exp = [54.598, 7.389, 1.000]                      sum=62.987
           p = [0.867, 0.117, 0.016]

T = 2.0 :  z/T = [1.0, 0.5, 0.0]
           exp = [2.718, 1.649, 1.000]                       sum=5.367
           p = [0.507, 0.307, 0.186]



The leader moved from 0.665 to 0.867 by halving the temperature, and down to 0.507 by doubling it. Note that temperature never reorders the candidates — the ranking is invariant — and it never assigns exactly zero to anything. That is the job of truncation, and it is why temperature and top-p are complementary rather than redundant knobs.

8 · Top-k truncation mathinteractive



Top-k sampling keeps the k highest-probability tokens, discards everything else, renormalizes, and samples:



Vk = top-k(p)     p̂i = pi / Σj∈Vk pj   for i ∈ Vk,   0 otherwise



It is simple, cheap, and it does what it says: the tail cannot be drawn. In implementation terms it is a partial sort — you do not need to sort all 50,000 logits, only find the k-th largest and mask below it.



Its weakness is that k is a constant while the model's confidence is not. Two situations, same k = 40:



    
  
  • A sharp step. The context is "The capital of France is". The model puts 0.98 on one token. Top-k with k = 40 still admits 39 alternatives holding a combined 0.02, and renormalization inflates their share slightly. You have manufactured a small chance of writing something false in a context where the model was certain.
    • 
  
  • A flat step. The context is "She opened the door and". Hundreds of continuations are genuinely plausible and no single token exceeds 0.05. Top-k with k = 40 throws away a large amount of legitimate probability mass and makes the output narrower than the model believes it should be.
    • 




So a fixed k is simultaneously too permissive when the model is confident and too restrictive when it is not. That observation is precisely what motivates top-p.




9 · Top-p (nucleus) truncation, and how it differs mathinteractive



Top-p sampling keeps the smallest set of tokens, taken in descending probability order, whose cumulative probability reaches at least p. Then renormalize and sample. Formally, sort so that p_(1) ≥ p_(2) ≥ … and take the nucleus



Vp = { first m tokens } where m = min { m : Σi=1m p(i) ≥ p }



The size of V_p is not fixed — it adapts to the shape of the distribution at that step. On the confident "capital of France" step the nucleus at p = 0.9 might contain a single token. On the wide-open "she opened the door and" step it might contain 300. That is the entire point: top-p asks "how much probability mass do I trust?" rather than "how many tokens do I trust?".



A worked truncation, by hand



Suppose a step yields these seven candidate probabilities, already sorted:



token   p       cumulative
A       0.40    0.40
B       0.25    0.65
C       0.15    0.80
D       0.10    0.90   <- cumulative first reaches 0.90 here
E       0.05    0.95
F       0.03    0.98
G       0.02    1.00



At p = 0.9 the nucleus is {A, B, C, D} — four tokens. The convention that matters: the token that crosses the threshold is included, so the kept mass is ≥ p, never less. Renormalizing by 0.90:



A: 0.40 / 0.90 = 0.4444
B: 0.25 / 0.90 = 0.2778
C: 0.15 / 0.90 = 0.1667
D: 0.10 / 0.90 = 0.1111
                 ------
                 1.0000



Compare with p = 0.8: cumulative reaches 0.80 at C, so the nucleus is {A, B, C} and renormalization divides by 0.80 giving [0.500, 0.3125, 0.1875]. Dropping p by 0.1 removed one token and pushed the leader from 0.444 to 0.500.




  Trap. Top-p is not "keep tokens with probability above p". A threshold on individual probabilities is a different, worse filter — it keeps nothing at all on a flat step where every token is below the threshold. Top-p thresholds the cumulative mass, which is why the nucleus is never empty.




Top-k and top-p are usually applied together, and the intersection is taken: k acts as a hard ceiling on how wide the nucleus can get on a very flat step, while p does the adaptive work. A common production setting is k = 50, p = 0.92, T = 0.9 — but treat any such triple as a starting point to be tuned against your own outputs, not a fact.

10 · Repetition penalties and n-gram blocking mathinteractive



Truncation controls which tokens are reachable but says nothing about tokens the model has already used. Two mechanisms attack repetition directly.



Repetition penalty (multiplicative on logits)



The standard formulation divides the logit of any already-generated token when the logit is positive, and multiplies when it is negative — so that in both cases the token is pushed down the ranking:



ẑi = zi / ρ   if zi > 0      ẑi = zi · ρ   if zi ≤ 0



with ρ ≥ 1; ρ = 1 disables it. The sign split exists because a plain division would raise a negative logit toward zero, boosting the very token you meant to suppress. That asymmetry is the part people get wrong when reimplementing it.



Worked example with logits z = [3.0, 1.5, 0.5, -0.5, -2.0], where tokens 0 and 3 have already appeared, at ρ = 1.5:



z0 =  3.0 > 0  ->  3.0 / 1.5 =  2.00
z3 = -0.5 ≤ 0  -> -0.5 * 1.5 = -0.75
others unchanged            ->  [2.00, 1.5, 0.5, -0.75, -2.0]

before:  p = [0.745, 0.166, 0.061, 0.023, 0.005]
after :  p = [0.523, 0.317, 0.117, 0.033, 0.010]



The repeated leader dropped from 0.745 to 0.523 and the runner-up nearly doubled. Push ρ to 2.0 and the first two tokens tie at 0.403 each. Push it much further and you start suppressing tokens that legitimately need to recur — articles, prepositions, the subject of the sentence — and the output becomes strained and thesaurus-like. Values above about 1.3 are aggressive; treat 1.05–1.2 as the working range and verify by reading outputs.



No-repeat n-gram blocking (hard constraint)



Set the probability of any token that would complete an n-gram already present in the generated text to exactly zero. With n = 3, if the text already contains "the coffee is", then after generating "the coffee" the token "is" is banned outright.



This is a blunt instrument. It guarantees no repeated trigram, which also means a legitimately repeated phrase — a name, a technical term, a refrain, a repeated table header — becomes impossible. For summarization of documents with recurring entity names it can do real damage. Use it when the repetition is pathological and a soft penalty has failed, and prefer larger n.

11 · The coherence–diversity trade-off math



Every knob in §7–§10 moves the output along one axis. It helps to name the two ends.




  
SettingMoves toward coherenceMoves toward diversity

  
Temperaturelower Thigher T

  
Top-ksmaller klarger k

  
Top-psmaller plarger p

  
Beam widthlarger B(none — B does not add diversity)

  
Repetition penalty(none — ρ trades fluency for variety)larger ρ





The trade-off is real and it is not a tuning failure you can engineer away. Concretely:



    
  
  • Turn everything toward coherence and you converge on greedy: safe, repetitive, and identical for every user. High measured fluency, near-zero information content.
    • 
  
  • Turn everything toward diversity and you converge on pure sampling: novel, occasionally brilliant, and derailing once every few hundred tokens.
    • 




The right operating point is a product decision, not a technical one, and it depends on the cost asymmetry of the two error types:



    
  
  • A customer-support reply. A wrong or invented sentence costs far more than a dull one. Sit near the coherent end: T ≈ 0.3, p ≈ 0.8, short max length, and ideally retrieval-grounded so the model is copying rather than composing.
    • 
  
  • A brainstorming or creative-drafting tool. A dull suggestion is worthless; a strange one is at least a prompt for the human. Sit near the diverse end: T ≈ 1.0–1.2, p ≈ 0.95, and generate several candidates so the user can discard the bad ones.
    • 
  
  • A summarizer. Coherent end, but for a different reason: any token that is not supported by the source is a hallucination, and diversity is exactly the mechanism that produces unsupported tokens.
    • 





  What to record. This is why the GenText service persists the decoding parameters alongside every generation. Without the settings, a rating of "this output was bad" is not actionable — you cannot tell whether the operating point was wrong or the model was. With the settings, the ratings become a labelled dataset over the parameter space, and you can find your own operating point instead of copying someone else's defaults.





12 · Perplexity: what it measures mathinteractive



Perplexity is the exponentiated average negative log-likelihood per token. For a sequence of N tokens where the model assigned probability p_t to the token that actually occurred:



PPL = exp( −(1/N) Σt=1N ln pt )



Equivalently, using base 2 and the cross-entropy H in bits per token, PPL = 2H. Both forms give the same number; only the logarithm base differs.



The interpretation worth memorizing: perplexity is the effective branching factor. A perplexity of 20 means the model was, on average, as uncertain as if it had been choosing uniformly among 20 equally likely tokens at every step. Perplexity 1 means perfect prediction. Perplexity equal to the vocabulary size means the model learned nothing.



A worked perplexity, by hand



Suppose the reference sentence is the cat sat on the mat and the model assigned these probabilities to those six tokens, each conditioned on everything before it:



t   token   p_t     ln p_t
1   the     0.50    -0.693147
2   cat     0.25    -1.386294
3   sat     0.20    -1.609438
4   on      0.40    -0.916291
5   the     0.50    -0.693147
6   mat     0.10    -2.302585
                    ----------
            sum  =  -7.600902



Average: -7.600902 / 6 = -1.266817. Negate and exponentiate:



PPL = e1.266817 ≈ 3.55



Sanity-check that against the geometric mean of the probabilities. The geometric mean is (0.50 × 0.25 × 0.20 × 0.40 × 0.50 × 0.10)1/6 = (0.0005)1/6 ≈ 0.2817, and 1 / 0.2817 ≈ 3.55. Perplexity is exactly the reciprocal of the geometric mean per-token probability — that is the whole definition, restated without logarithms.



Now change one number. Make the model's probability for "mat" 0.001 instead of 0.10. Then ln 0.001 = -6.907755, the sum becomes -12.206072, the average -2.034345, and PPL = e2.034345 ≈ 7.65. One badly predicted token out of six more than doubled the perplexity. Perplexity is dominated by the tokens the model got most wrong, because -ln p grows without bound as p → 0. A single token with p = 10-9 contributes +20.7 to the sum on its own.

What perplexity does not measure



This is the part that matters for your evaluation section, and it is the part that gets skipped.



    
  
  • It is not comparable across tokenizers. Perplexity is per token. A model with a bigger vocabulary uses fewer tokens for the same text and will report a different perplexity for identical predictive quality. Two perplexity numbers from two tokenizers are not comparable, full stop. (Per-character or per-word normalization fixes this; report which you used.)
    • 
  
  • It is not comparable across corpora. Perplexity on formulaic text is low because formulaic text is predictable. A model scoring 12 on product listings is not better than one scoring 40 on novels.
    • 
  
  • It says nothing about generated text. Perplexity scores a model against a reference corpus it did not write. It is a measure of predictive fit, not of output quality. You cannot compare decoding strategies with it in any meaningful way.
    • 
  
  • Low perplexity on your own output is a warning sign, not a success. If you compute the perplexity of a generation under the model that produced it, greedy decoding will always score lowest — it selected the highest-probability token at every step by construction. That is a tautology, not evidence of quality, and it is the single most common evaluation mistake in this topic.
    • 
  
  • It is blind to truth, safety, and relevance. A fluent, confident, entirely fabricated biography has excellent perplexity.
    • 





  Trap. "We tuned our decoding settings by minimizing perplexity" is a self-defeating experiment. It will select T → 0 every time, because that maximizes the likelihood of exactly the tokens you chose to emit. Use perplexity to compare models or fine-tuning runs on a fixed held-out reference set. Use human ratings and diversity metrics to compare decoding settings.





13 · Automatic diversity metrics: distinct-n mathinteractive



Perplexity cannot see repetition. Diversity metrics can, and they are cheap. The workhorse is distinct-n: the number of unique n-grams divided by the total number of n-grams.



distinct-n = |unique n-grams| / |total n-grams|



Compute it for the greedy output from §4, the coffee is rich and smooth and smooth and smooth (10 tokens):



distinct-1 : unique unigrams {the, coffee, is, rich, and, smooth} = 6, total 10  -> 0.600
distinct-2 : unique bigrams {the coffee, coffee is, is rich, rich and,
                             and smooth, smooth and}             = 6, total  9  -> 0.667
distinct-3 : unique trigrams                                     = 6, total  8  -> 0.750



Contrast a sampled output of similar length, the coffee tastes smooth and rich but not too bitter: every unigram is unique, so distinct-1 = 1.000. The gap between 0.600 and 1.000 is the loop, detected without a human reading anything.



Three things to be careful about:



    
  
  • Distinct-n is length-dependent. Longer texts reuse function words, so distinct-n falls mechanically as length grows. Only compare distinct-n across generations of comparable length, or report it alongside length.
    • 
  
  • High distinct-n is not good writing. Random tokens score 1.000 on every order. Distinct-n is a repetition detector, not a quality metric. It belongs next to a coherence signal, never alone.
    • 
  
  • Corpus-level diversity is a separate question. Distinct-n within one output does not detect the beam-search failure where different prompts produce near-identical outputs. For that, measure across generations: how many of your 20 outputs share a 4-gram with another output? That is where beam search's diversity collapse becomes visible.
    •

Other automatic signals worth knowing by name: self-BLEU (BLEU of each generation against all the others — high self-BLEU means your outputs are copies of each other), type-token ratio (distinct-1 under another name), and mean segmented type-token ratio, which fixes the length dependence by averaging TTR over fixed-length windows. All of them measure surface variety. None measures whether the text is correct.




14 · Human rating, and disagreement as data interactive



Automatic metrics can tell you that text is repetitive. They cannot tell you that it is wrong, off-tone, unhelpful, or subtly offensive. That is why the topic project requires human ratings, and why the requirement is two independent raters per output rather than one.



Design the rubric before you generate



A rubric written after you have read the outputs will be shaped by them. Fix the dimensions first. A workable set for a generation service, each on a 1–5 scale, each with anchor descriptions for at least points 1, 3, and 5:



    
  
  • Fluency — is it grammatical and readable, ignoring content? (Rate this without judging truth; separating fluency from correctness is the point.)
    • 
  
  • Coherence — does it stay on one topic and hold together across sentences?
    • 
  
  • Relevance — does it answer the prompt, rather than a nearby question?
    • 
  
  • Factual support — are the specifics it asserts supported, or invented? Mark "not applicable" for purely creative prompts rather than guessing.
    • 
  
  • Would you ship it — a single binary. This is the most useful column and the one most often left out.
    • 




Rate blind: the rater should not see the decoding parameters, and outputs from different settings should be shuffled together. If a rater knows an output came from T = 1.4, they will find it wilder.



Disagreement is a measurement, not a nuisance



The instinct is to average the two raters and move on. Do not — or at least, not before you have looked at where they differed. Disagreement carries information that agreement does not:



    
  
  • A whole dimension with low agreement means the rubric is underspecified. If your two raters agree on fluency and disagree constantly on coherence, the coherence anchors are vague. Fix the rubric and re-rate; do not report a mean over a dimension your raters could not apply consistently.
    • 
  
  • A handful of items with large disagreement is usually the most interesting subset in the whole study. Those are the genuinely ambiguous outputs — plausible but unverifiable, fluent but off-tone. Read them; they are where the failure modes live.
    • 
  
  • Systematic offset — one rater consistently one point above the other on everything — is a calibration problem, not a disagreement about content. It disappears if you compare rankings instead of absolute scores, and it is a reason to prefer pairwise A/B comparisons over absolute scales when you can afford them.
    • 




Reporting agreement



Report at least three numbers, not one:



    
  
  • Exact agreement — the fraction of items where the two scores are identical.
    • 
  
  • Adjacent agreement — the fraction within one point. On a 1–5 ordinal scale this is often the more honest number.
    • 
  
  • Cohen's κ — agreement corrected for what chance alone would produce: κ = (p_o - p_e) / (1 - p_e), where p_o is observed agreement and p_e is the agreement expected from the two raters' marginal score distributions.
    • 




Unweighted κ treats a 4-vs-5 disagreement as exactly as bad as a 1-vs-5 disagreement, which is wrong for an ordinal scale. Use a weighted κ — quadratic weights are standard for rating scales — and say which you used. The widget computes all of them so you can see how far apart they can be on the same data.

  How many ratings do you need? The project asks for at least 20 outputs scored independently by two people. That is enough to detect a large difference between two decoding settings and to surface failure modes. It is not enough to claim a small difference is real. If your two settings score 3.4 and 3.6 on twenty items, the honest conclusion is "we could not distinguish them", and that is a perfectly good result to report.





15 · Failure modes you will actually see



Four failure modes account for most of what goes wrong in an undergraduate generation project. Learn to name them on sight, because "the output was bad" is not a report and "the output echoed the prompt and then truncated mid-clause" is.



Degenerate repetition


Looks like: a word, phrase, or sentence repeating until the length cap. ...and smooth and smooth and smooth.


Cause: a deterministic or near-deterministic decoder re-entering a state it has visited (§4), amplified by the model's own tendency to raise the probability of a span each time it recurs.


Fix: stop using greedy or narrow beams for open-ended text; add sampling; add a repetition penalty around 1.1–1.2; as a last resort, block repeated 4-grams. Detect it automatically with distinct-2 (§13) — a value under about 0.7 on a short output is a strong signal.



Hallucinated specifics


Looks like: fluent text containing a precise, checkable, false detail — a date, a statistic, a citation, a version number, a person's title.


Cause: the model has no mechanism for distinguishing "I know this" from "this is the shape of a sentence that usually appears here". Specific-looking tokens are high-probability continuations of specific-looking contexts. Raising temperature makes it worse by giving low-probability specifics a real chance of being drawn.


Fix: lower temperature and tighten p; ground the generation in retrieved source text so the model is copying rather than composing; and — the only reliable one — verify specifics outside the model. Note carefully that no decoding setting eliminates this. Truncation removes the tail, and hallucinations frequently come from the head of the distribution.



Prompt echo


Looks like: the output restates the prompt, sometimes verbatim, before saying anything new — or says nothing new at all.


Cause: two different things that look identical, and you must distinguish them. (1) A plumbing bug: many generation APIs return the prompt concatenated with the continuation, and you forgot to slice it off. Check output[len(input_ids):] before diagnosing anything else. (2) A genuine modelling issue: for a base (non-instruction-tuned) model, continuing the prompt's own phrasing really is a high-probability continuation, especially at low temperature.


Fix: slice the prompt off the output; if it is genuine, restructure the prompt so that continuing it verbatim is not natural (end mid-sentence, or use an instruction-tuned checkpoint), and raise temperature slightly.



Abrupt truncation


Looks like: the output stops mid-sentence or mid-clause.


Cause: almost always max_new_tokens being hit. Two subtler causes: beam search without a length penalty is biased toward emitting the end-of-sequence token early (§5); and an early end-of-sequence draw from an under-truncated distribution can end the generation at any moment.


Fix: raise the length cap and confirm the output now ends on punctuation; set a length penalty if you are using beams; if you must cut, truncate at the last sentence boundary rather than mid-clause, and record that you did so.

16 · A decoding recipe for the GenText service code



Putting the topic together as something you can implement. The service exposes decoding controls to a non-expert, so the controls need sane defaults, safe ranges, and an explanation attached to each.



from dataclasses import dataclass

@dataclass
class DecodeConfig:
    strategy: str = "sample"      # "greedy" | "beam" | "sample"
    temperature: float = 0.9      # ignored when strategy != "sample"
    top_k: int = 50               # 0 disables
    top_p: float = 0.92           # 1.0 disables
    repetition_penalty: float = 1.1
    max_new_tokens: int = 120
    num_beams: int = 1            # > 1 only when strategy == "beam"
    seed: int | None = None       # record it, or you cannot reproduce anything

    def validate(self) -> None:
        assert 0.0 < self.temperature <= 2.0
        assert 0.0 < self.top_p <= 1.0
        assert self.top_k >= 0
        assert 1.0 <= self.repetition_penalty <= 2.0
        assert 1 <= self.max_new_tokens <= 512
        if self.strategy == "beam":
            assert self.num_beams > 1



Three service-level points that are easy to skip and expensive to add later.



Record the seed


Sampling is stochastic. If you do not store the random seed with the generation, you cannot reproduce an output a rater flagged, and you cannot demonstrate that a settings change caused a difference rather than luck. Store it as a first-class column next to the decoding parameters.



Store parameters with every row, not per session


The history view is only useful if each row is self-describing: prompt (hashed), every decoding parameter, the model version, the output, the timestamp, and the rating once it exists. If the parameters live in a session config instead, a change to that config silently rewrites the meaning of every historical row.



Make the comparison view fix the seed


A "compare decoding strategies" tab that samples independently for each setting is comparing settings and noise. Use the same seed across the strategies being compared so the difference you show the user is attributable to the parameters. Say so in the UI, because it is a real caveat: one seed is one sample, and a single side-by-side is an illustration, not evidence.




  Order of operations, once more. repetition penalty on raw logits → divide by temperature → top-k mask → top-p mask → renormalize → sample. If your outputs do not respond to a knob the way these notes say they should, check this order first. It is the most common source of "temperature does nothing" bug reports.
