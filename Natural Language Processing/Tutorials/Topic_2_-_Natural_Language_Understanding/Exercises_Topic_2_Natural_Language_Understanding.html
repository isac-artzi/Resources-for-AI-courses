By hand · representation

1 · A bag-of-words vector by hand warm-up

Take these two documents, lowercased, punctuation stripped, no stop-word removal, no stemming:

A: the refund was processed but the item was not returned
B: the item was returned but the refund was not processed
  1. Write the shared vocabulary in alphabetical order and give |V|.
  2. Write the count vector for A and for B in that order.
  3. Compute the cosine similarity between them.
  4. These two sentences describe opposite situations, one of which entitles the customer to money. What does your answer to part 3 imply about any classifier built on this representation?
Show solution

1. Both documents contain exactly the same multiset of tokens. The vocabulary, alphabetically, is:

but, item, not, processed, refund, returned, the, was      →  |V| = 8

2. Counting in that order, each document has 10 tokens:

A = [1, 1, 1, 1, 1, 1, 2, 2]
B = [1, 1, 1, 1, 1, 1, 2, 2]

3. The vectors are identical, so the cosine is exactly 1:

dot(A, B) = 1+1+1+1+1+1+4+4 = 14
|A| = |B| = sqrt(14)
cos = 14 / (sqrt(14) * sqrt(14)) = 14/14 = 1.0000

4. Identical vectors means identical input to the classifier, which means identical output. No TF–IDF weighting, no regularization setting, no amount of extra training data can separate them: a function cannot return two different values for one input. The only fixes are representational — bigrams (not returned versus not processed become distinct features), a negation-marking preprocessing pass, or a model that reads word order, which is the argument for the encoder.

2 · TF–IDF for a whole document warm-up

A corpus of five app-store reviews, N = 5:

d1: the app crashed on launch
d2: the app crashed again after the update
d3: great app, no issues at all
d4: the update fixed my issues
d5: launch day was smooth

Using tf(t, d) = count(t, d) / |d| and idf(t) = log10(N / df(t)):

  1. Compute df for every term of d1.
  2. Produce the full tf–idf table for d1, sorted from largest to smallest.
  3. Which term scores highest? Is that the term you would want a complaint classifier to lean on? Explain what went wrong and name two fixes.
Show solution

1. d1 has five tokens: the, app, crashed, on, launch, so |d1| = 5 and every count is 1. Document frequencies over all five documents:

the      → d1, d2, d4      → df = 3
app      → d1, d2, d3      → df = 3
crashed  → d1, d2          → df = 2
on       → d1              → df = 1
launch   → d1, d5          → df = 2

2. Every tf is 1/5 = 0.2000, so the ranking is decided entirely by idf.

termcounttfdfidf = log10(5/df)tf–idf
on10.200010.69900.1398
crashed10.200020.39790.0796
launch10.200020.39790.0796
the10.200030.22180.0444
app10.200030.22180.0444

Worked arithmetic for the top row: idf(on) = log10(5/1) = log10(5) = 0.6990, and 0.2000 × 0.6990 = 0.1398.

3. The winner is on, a preposition with no bearing on whether the review is a complaint. TF–IDF measures distinctiveness within this corpus, not meaning, and on happens to occur in exactly one of five documents. This is a small-corpus artifact: with 5,000 reviews, on would appear in a large fraction of them and its idf would collapse toward zero, while crashed would stay comparatively rare. Two fixes: (a) use a corpus large enough for document frequencies to be stable — the reason the topic project sets a 5,000-row floor; (b) set min_df above 1 so hapax terms are dropped, or apply a stop-word list. A third option is to let the classifier handle it: logistic regression can learn a near-zero weight for on, provided it has enough examples to see that the term is uninformative.

Sample arithmetic: log10(5/3) = log10(1.6667) = 0.2218; ln(5/3) = 0.5108; and ln(6/4) + 1 = ln(1.5) + 1 = 0.4055 + 1 = 1.4055.

    
Term in every document (df = N). Under both textbook forms the idf is exactly 0, so the tf–idf of that term is 0 in every document and the feature is dead — idf acting as an automatic stop-word filter. Under the scikit-learn form the idf is exactly 1, so the feature survives with its raw tf.

    
Why the smoothed form. Two reasons. First, robustness: the +1 in the denominator behaves as if an extra document containing every term had been added, so a term unseen in the training corpus cannot produce a division by zero when the vectorizer is applied to new text. Second, keeping the value non-zero avoids silently discarding a column: a term present everywhere in this corpus may still be worth keeping, and after the L2 normalization that TfidfVectorizer applies by default it will contribute little to the direction of the vector anyway. Note the consequence for reproducibility — numbers computed by hand with the textbook formula will not match scikit-learn's output, and that is not a bug in either.

4 · A linear classifier's score by hand core

  

    
A logistic-regression complaint detector (label 1 = complaint) has learned these weights, with bias b = −0.30:

    
w(refund) = +2.10    w(broken) = +1.60
w(thanks) = -2.40    w(quick)  = -1.10

    
An incoming message produces the TF–IDF features refund = 0.50 and thanks = 0.40; every other coordinate is 0.

    
    
      
  1. Compute z and p = σ(z) to four decimal places.
    2. 
      
  2. What label is predicted at a threshold of 0.5? At a threshold of 0.4?
    3. 
      
  3. What bias b would place this exact message on the decision boundary?
    4. 
      
  4. The vocabulary has 30,000 entries. How many multiplications did part 1 actually require, and why?
    5. 
    

  

  

    Show solution
    
1. Only the two non-zero coordinates contribute:

    
z = (2.10)(0.50) + (-2.40)(0.40) + (-0.30)
  = 1.05 - 0.96 - 0.30
  = -0.2100

p = 1 / (1 + e^0.21) = 1 / (1 + 1.2337) = 1 / 2.2337 = 0.4477

    
2. At threshold 0.5: 0.4477 < 0.5, so predict 0 (not a complaint). At threshold 0.4: 0.4477 ≥ 0.4, so predict 1. Same model, same input, opposite decision — which is why a reported recall without a stated threshold is meaningless.

    
3. On the boundary p = 0.5, which is exactly z = 0:

    
0 = 1.05 - 0.96 + b   →   b = -0.09

    
Raising the bias from −0.30 to −0.09 tips this message to the boundary; anything above −0.09 flags it. Shifting the bias and moving the threshold are the same operation viewed from two sides.

    
4. Two. The dot product runs over the non-zero entries of a sparse vector, and this document has two. That is the whole reason the classical pipeline answers in microseconds regardless of vocabulary size: cost scales with document length, not with |V|.

  3. The team's report says "85% accurate". Write the one additional sentence that turns that into an honest summary.

  4. Support staff complain that they are chasing too many non-complaints. Which metric are they describing, and which way should the threshold move?

    Show solution
    
1. TP = 180, FN = 60, FP = 120, TN = 840, n = 1,200.

    
accuracy  = (180 + 840) / 1200 = 1020/1200 = 0.8500
precision = 180 / (180 + 120) = 180/300 = 0.6000
recall    = 180 / (180 + 60)  = 180/240 = 0.7500

3. 6 · Imbalance and the crossover prevalence core

  

    
A safety-flag classifier runs on 5,000 held-out messages. The true prevalence of the positive class is 2%. Your detector has a true-positive rate (recall) of 0.80 and a false-positive rate of 0.04.

    
    
      
  1. How many messages are truly positive and truly negative?
    2. 
      
  2. Fill in the confusion matrix for the detector and compute accuracy, precision, recall and F1.
    3. 
      
  3. What accuracy does a model that always predicts 0 achieve on this data?
    4. 
      
  4. Above what prevalence would the detector beat the do-nothing model on accuracy? Derive it, then say what your answer means for using accuracy as the headline metric here.
    5. 
    

  

  

    Show solution
    
1. Positives = 0.02 × 5,000 = 100; negatives = 4,900.

    
2. TP = 0.80 × 100 = 80, so FN = 20. FP = 0.04 × 4,900 = 196, so TN = 4,704.

    

      
predicted 1predicted 0

      
actual 18020

      
actual 01964704

    

    
accuracy  = (80 + 4704)/5000 = 4784/5000 = 0.9568
precision = 80/(80 + 196) = 80/276          = 0.2899
recall    = 80/(80 + 20)  = 80/100          = 0.8000
F1        = 2(0.2899)(0.8000)/(0.2899 + 0.8000)
          = 0.4638/1.0899                    = 0.4255

    
Precision of 0.29 means roughly seven of every ten flags are false alarms — a direct consequence of the negative class being 49 times larger, not of the detector being poor.

    
3. Always predicting 0 scores 4,900/5,000 = 0.9800, which is higher than the detector's 0.9568.

    
4. Write both accuracies as functions of prevalence p:

    
accuracy(do-nothing) = 1 - p
accuracy(detector)   = p·TPR + (1 - p)(1 - FPR)

detector wins  ⟺  p·TPR + (1-p)(1-FPR) > 1 - p
               ⟺  p·TPR > (1-p)·FPR
               ⟺  p > FPR / (TPR + FPR) = 0.04 / 0.84 = 0.0476

    
The crossover is 4.76%. At the actual 2% prevalence the detector loses on accuracy to a function that reads none of its input, catches nothing, and could be written on one line. Accuracy is therefore the wrong headline here: report the confusion matrix, precision, recall and F1 on the positive class, and state the do-nothing baseline explicitly so the reader can see the floor.

8 · Temperature scaling: predict, then check core

  

    
A binary classification head produces the logits z = [z0, z1] = [1.20, 3.00].

    
    
      
  1. Compute p1 at T = 1 using the identity p1 = σ(z1 − z0), to four decimals.
    2. 
      
  2. Predict, before computing, whether T = 2 raises or lowers p1, and whether it changes the predicted label. Then compute p1 at T = 2 and at T = 0.5.
    3. 
      
  3. Add 5 to both logits and recompute at T = 1. Explain the result in one sentence.
    4. 
      
  4. If this model's held-out ECE is 0.11 with mean confidence above accuracy, would you fit T > 1 or T < 1? What happens to F1 as a result?
    5. 
    

  

  

    
Widget · two logits, one temperature

    

      

        

      

        

      

        

      
    

    

  

  

    Show solution
    
1. z1 − z0 = 1.80, so

    
p1 = sigma(1.80) = 1/(1 + e^-1.80) = 1/(1 + 0.1653) = 0.8581

    
2. Dividing by T = 2 halves the logit difference to 0.90, which pulls the distribution toward uniform, so p1 must fall — but it stays above 0.5, so the predicted label is unchanged. A temperature can never flip a binary prediction, because dividing by a positive number cannot change the sign of the difference.

    
T = 2.0 :  p1 = sigma(1.80/2)   = sigma(0.90) = 0.7109
T = 0.5 :  p1 = sigma(1.80/0.5) = sigma(3.60) = 0.9734

    
3. With z = [6.20, 8.00] the difference is still 1.80, so p1 = 0.8581, exactly as before. A two-class softmax depends only on the difference of the logits; their absolute magnitudes carry no information, which is why you can never judge a model's confidence by looking at a raw logit.

    
4. Mean confidence above accuracy means the model is overconfident, so you want to soften the distribution: fit T > 1. F1 is unchanged. Dividing every logit by the same positive scalar preserves the ordering of scores and cannot move any prediction across the argmax, so the confusion matrix at the argmax decision is identical. (If you classify by comparing p1 to a fixed threshold other than 0.5, then rescaling does move examples across it, and you should re-select the threshold after calibrating.)

9 · Code: TF–IDF in pure Python core

  

    
Write tfidf_row(docs, i) using only the standard library. It takes a list of raw document strings and an index, and returns a dict mapping every term of docs[i] to its tf–idf weight, where tf = count / |d| and idf = log10(N / df). Lowercase the text and strip everything that is not a letter, digit, apostrophe or space.

    
Run it on the corpus below and print each term with its weight to four decimals, sorted from largest to smallest.


corpus = [
    "the service was slow and the food was cold",
    "the food was excellent and the service was fast",
    "slow service ruined the meal",
    "excellent meal and excellent service",
]

    
Expected output (this is the same corpus computed by hand in section 4 of the notes, so your program is checkable against pencil and paper):


was        0.0669
cold       0.0669
slow       0.0334
food       0.0334
the        0.0278
and        0.0139
service    0.0000

  

  

    Show solution

import math, re
from collections import Counter

def tokenize(text):
    return re.sub(r"[^a-z0-9' ]+", " ", text.lower()).split()

def tfidf_row(docs, i):
    toks = [tokenize(d) for d in docs]
    N = len(toks)
    df = Counter()
    for t in toks:
        df.update(set(t))          # set() first: df counts documents, not occurrences
    counts = Counter(toks[i])
    n = len(toks[i])
    return {term: (c / n) * math.log10(N / df[term])
            for term, c in counts.items()}

corpus = [
    "the service was slow and the food was cold",
    "the food was excellent and the service was fast",
    "slow service ruined the meal",
    "excellent meal and excellent service",
]

for term, w in sorted(tfidf_row(corpus, 0).items(), key=lambda kv: -kv[1]):
    print(f"{term:10s} {w:.4f}")

    
Three places this goes wrong if you are not careful:

    
    
      
  • df.update(set(t)), not df.update(t). Document frequency counts documents containing the term, not occurrences. Without set(), the would get df = 5 in a four-document corpus — and log10(4/5) is negative, silently inverting the sign of the feature.
    • 
      
  • Divide by the token count, not the distinct-term count. Here |d1| = 9 tokens but only 7 distinct terms; using 7 changes every value.
    • 
      
  • math.log10, not math.log. Natural log gives values 2.303× larger. The ranking is identical, but the numbers will not match the hand computation.
    • 
    

    
Confirm the two ties in the output: was scores 0.0669 with count 2 and df 2, while cold scores the same with count 1 and df 1 — half the term frequency, twice the idf. And service is exactly 0.0000 because it occurs in all four documents.

10 · Code: metrics from four counts core

  

    
Write report(tp, fn, fp, tn) returning a dict with keys n, accuracy, precision, recall, f1, each rounded to four decimals, and returning None for precision or recall when the denominator is zero (F1 is 0.0 in that case). Do not import anything.

    
Then call it twice and print the results:


print(report(180, 60, 120, 840))
print(report(0, 60, 0, 1940))

    
Expected output:


{'n': 1200, 'accuracy': 0.85, 'precision': 0.6, 'recall': 0.75, 'f1': 0.6667}
{'n': 2000, 'accuracy': 0.97, 'precision': None, 'recall': 0.0, 'f1': 0.0}

    
The second line is the do-nothing classifier from problem 6. Say in one sentence what a dashboard that renders None as 0.00 would hide from its reader.

  

  

    Show solution

def report(tp, fn, fp, tn):
    n = tp + fn + fp + tn
    acc = (tp + tn) / n
    prec = tp / (tp + fp) if (tp + fp) else None
    rec  = tp / (tp + fn) if (tp + fn) else None
    f1 = 2 * prec * rec / (prec + rec) if prec and rec else 0.0
    return {
        "n": n,
        "accuracy": round(acc, 4),
        "precision": None if prec is None else round(prec, 4),
        "recall": None if rec is None else round(rec, 4),
        "f1": round(f1, 4),
    }

    
Points to check in your version:

    
    
      
  • if (tp + fp) guards the zero denominator. A model that never predicts the positive class has undefined precision — there is no set of positive predictions to be right about.
    • 
      
  • if prec and rec also handles the case where both are defined but one is 0.0, which would otherwise be a division by zero in the F1 formula.
    • 
      
  • round(0.6, 4) prints as 0.6, not 0.6000. Python drops trailing zeros in the repr; that is cosmetic, and matching the expected output above means not adding formatting that changes the values.
    • 
    

    
The dashboard question. Rendering None as 0.00 makes "the model never fired at all" look identical to "the model fired and was always wrong". Those are different failures with different fixes — the first is a broken threshold or a collapsed model, the second is a genuinely bad classifier — and the display would have erased the distinction. Print the raw confusion matrix next to the metrics and the ambiguity disappears.

You are fine-tuning distilbert-base-uncased for single-label binary classification with only 900 labeled examples, so you decide to freeze the embedding table and the bottom four of the six encoder layers.

    
    
      
  1. Write the code that loads the model with two labels, applies that freezing, and prints trainable and total parameter counts with the trainable percentage to one decimal.
    2. 
      
  2. Compute the expected numbers by hand first. A DistilBERT encoder layer has 4d2 + 4d attention parameters, 2df + f + d feed-forward parameters and 4d layer-norm parameters, with d = 768 and f = 3072. The embeddings are 30522d + 512d + 2d. The head is d2 + d (pre-classifier) plus 2d + 2 (classifier).
    3. 
      
  3. Explain why the warning about newly initialized classifier weights on the first load is expected, and when the same warning would indicate a real problem.
    4. 
    

    
Expected output:


14,767,874 / 66,955,010 trainable (22.1%)

  

  

    Show solution
    
1.


from transformers import AutoModelForSequenceClassification

model = AutoModelForSequenceClassification.from_pretrained(
    "distilbert-base-uncased", num_labels=2)

for p in model.distilbert.embeddings.parameters():
    p.requires_grad = False
for layer in model.distilbert.transformer.layer[:4]:
    for p in layer.parameters():
        p.requires_grad = False

trainable = sum(p.numel() for p in model.parameters() if p.requires_grad)
total     = sum(p.numel() for p in model.parameters())
print(f"{trainable:,} / {total:,} trainable ({100 * trainable / total:.1f}%)")

    
2. Per encoder layer, with d = 768, f = 3072:


attention   : 4(768²) + 4(768)          = 2,359,296 + 3,072   = 2,362,368
feed-forward: 2(768)(3072) + 3072 + 768 = 4,718,592 + 3,840   = 4,722,432
layer norms : 4(768)                                          =     3,072
                                                                ----------
                                                                 7,087,872

embeddings  : 30522(768) + 512(768) + 2(768)                  = 23,835,648
head        : 768² + 768 + 2(768) + 2 = 590,592 + 1,538       =    592,130

total       : 6(7,087,872) + 23,835,648 + 592,130             = 66,955,010
trainable   : 2(7,087,872) + 592,130                          = 14,767,874
percentage  : 100 × 14,767,874 / 66,955,010                   =      22.1%

    
Two layers plus the head is about a fifth of the model. With 900 examples that is the right order of magnitude — unfreezing all 67 million parameters gives the model enough capacity to memorize the training set in two or three epochs.

    
3. The warning appears because distilbert-base-uncased was pretrained with a masked-language-model head, not a classification head. pre_classifier and classifier do not exist in the checkpoint, so from_pretrained creates them from scratch and tells you so. That is correct and expected on the first load. The same warning is a real problem if it appears when you load your own fine-tuned checkpoint for inference: it means the classification weights you trained were not found, you are serving a random head, and your production accuracy will be near chance while your training logs look fine. Check the path you saved to, and confirm the directory contains the model weights and config.

12 · Explain: the metric a stakeholder should see stretch

  

    
Your team ships a binary classifier that routes incoming support messages to either an automated resolution path or a human queue. Roughly 8% of messages are eligible for automation. A product manager asks for "one number that tells me if it is working" and proposes accuracy.

    
Write a short answer (150–250 words) that: (a) explains concretely, with numbers from this setup, why accuracy alone will mislead; (b) proposes what you would put on the dashboard instead and why; and (c) names one situation in which accuracy would be the right headline.

  

  

    Show solution
    
(a) Why accuracy misleads here. With 8% eligible, a classifier that routes everything to the human queue — reading nothing, learning nothing — is 92% accurate. Any real model's accuracy is therefore trapped in a narrow band near 92%, where a movement of one point can mean a large change in behavior on the class that matters. Worse, the two errors have completely different costs: a false positive automates a message that needed a human, which can mean a customer's real issue is closed unread; a false negative sends an automatable message to a person, which costs a few minutes. Accuracy adds these together with equal weight, which is exactly wrong.

    
(b) What to put on the dashboard. The 2×2 confusion matrix in raw counts, plus precision and recall on the positive (automatable) class at a stated threshold, plus the do-nothing baseline accuracy for reference. Precision is the metric tied to the expensive error, so it should be the headline, with a service level attached: for example "precision ≥ 0.98 at whatever recall that costs". Add the ECE so the displayed probabilities are known to mean something, and add class prevalence per period so drift is visible.

    
(c) When accuracy is right. When the classes are roughly balanced and the two error types cost about the same — for instance routing between two equally staffed queues where a mis-route in either direction costs one transfer. Then accuracy is a fair summary and its simplicity is a genuine advantage.

  







  
Explain · model choice

  
13 · Explain: 1,000 labels and no GPU stretch

  

    
You have 1,000 labeled examples of short in-domain text, a CPU-only server, and a hard requirement of under 50 ms per prediction at the ninety-fifth percentile. Decide between fine-tuning a pretrained encoder and training TF–IDF with logistic regression.

    
Justify your choice using at least two constraints, then describe one realistic situation in which your choice would be the wrong one and the other option would win. There is no single correct answer; the reasoning is what is being assessed.

  

  

    Show solution
    
A defensible answer: start with TF–IDF and logistic regression.

    
Constraint 1 — latency. A prediction from the classical pipeline is a tokenization pass plus a dot product over a few dozen non-zero features: well under a millisecond on a CPU. A DistilBERT forward pass on a CPU is typically tens of milliseconds and is sensitive to sequence length and load, so a 50 ms budget at the ninety-fifth percentile is a genuine risk rather than a formality. The classical model meets the requirement with room to spare.

    
Constraint 2 — data volume against capacity. 1,000 examples against 67 million parameters is a memorization risk that has to be managed with frozen layers, early stopping and a validation split you can barely afford to carve out — a 200-example validation set gives noisy metrics, so you will struggle to tell a real gain from run-to-run variance.

    
Constraint 3 — cost and operational surface. The classical model trains in seconds, retrains on a schedule with no GPU, produces readable weights you can show a reviewer, and adds no model-loading time to a cold start.

    
Where this choice is wrong. If the label depends on negation, word order or paraphrase — "I did not receive a refund" versus "I received a refund" — the bag-of-words vectors are close or identical and the linear model has no route to the right answer, while the encoder handles it directly. Also, if the deployment text uses vocabulary the 1,000 training documents never contain (new product names, a different customer segment, misspellings), the closed vocabulary drops those terms entirely while subword tokenization degrades gracefully. In either case the encoder wins by enough to justify the cost, and the answer is to fine-tune, then handle latency with distillation, quantization, batching, or by keeping the classical model as a fast path and escalating only uncertain cases.

    
The move that settles it. Build the classical baseline first — it takes an afternoon — and use its error analysis as evidence. If most errors are negation and paraphrase, you have a measured argument for the encoder rather than an assumption.

  







  
Explain · calibration

  
14 · Explain: what the score in the API response means stretch

  

    
Your service returns:


{"label": "complaint", "score": 0.94, "model_version": "distilbert-ft-v3"}

    
An operations lead proposes a rule: auto-escalate anything with a score above 0.90, and tells the team this will be wrong "about one time in ten".

    
    
      
  1. Explain why that inference is not supported by the number, in terms a non-specialist can follow.
    2. 
      
  2. Describe the measurement you would run to find out whether it is true, including which data split you would use.
    3. 
      
  3. State what you would change in the service so the rule becomes defensible.
    4. 
    

  

  

    Show solution
    
1. The 0.94 comes out of a softmax, which is a function that takes two arbitrary real numbers and rescales them so they are positive and add to one. That guarantees the output looks like a probability; it does not make the number equal to the frequency of being right. The training objective rewards ranking the correct class above the wrong one, and nothing in it forces "0.94" to correspond to 94 correct out of 100. Empirically, networks fine-tuned to low training loss are usually overconfident, and the effect gets stronger the longer you train on a small corpus. So the rule's premise — "0.94 means about one error in ten above 0.90" — is a claim about the world that nobody has measured.

    
2. Measure calibration on a held-out split that was used for neither training nor threshold selection. Collect the predictions, sort them into ten bins by confidence, and in each bin compare the mean stated confidence against the observed fraction correct. Plot the pairs against the diagonal (a reliability diagram) and summarize with expected calibration error, ECE = Σb (nb/n) |accuracy(b) − confidence(b)|, alongside the Brier score. The number that answers the operations lead directly is the observed accuracy of the single bin above 0.90. If the model states 0.94 there and is right 82% of the time, the rule is wrong about one time in five, not one in ten.

    
3. Three changes. (a) Fit a temperature on a dedicated calibration split by minimizing negative log-likelihood over that one parameter, and apply it before the softmax in the service; this leaves the predicted labels and therefore accuracy, precision, recall and F1 unchanged while making the numbers mean what they say. (b) Return the calibrated probability in the response, and record in the model card the ECE before and after and the date of the calibration split. (c) Re-measure on a schedule, because calibration drifts when the input distribution moves even if accuracy looks stable — and log every prediction so the check can be reproduced later against real traffic.
